# 归档：收藏作者「全局 feed + 连续区」方案（**已停止开发**）

- **分支**：`feature/favorite-authors`（本文件的所在分支）
- **归档时间**：2026-11-14
- **状态**：**停止开发**，仅保留作对照与代码参考，**不要再在此分支上继续**
- **被取代**：`master` 上的「按作者拉取 + 每作者游标」方案
  （提交 `08fb72e`；服务 `Services/Online/WtLiveAuthorFeedCache.cs`）

---

## 一、这个方案当时想做什么

需求：在「收藏的作者」浮窗加一个按钮，看**所有收藏作者**的涂装。

站点**没有**"多个作者合并查询"的接口，也不能把多个 id 塞进一次 `user=` 查询。于是选了这条路：

1. 清空筛选、把排序设成站点默认（`created`）= **全局原始 feed**；
2. 每页 25 条在**本地**按收藏作者集合过滤；
3. 某页零命中就继续翻页，直到命中够一批 / 页数上限 / 站点到底；
4. 为了省请求，给列表元数据做了 gzip JSONL 缓存（`WtLiveFeedCache`），
   并引入"**连续区**"概念：只把"从第 0 页顺序取过的页"当作可展示区，其它条目只用于去重；
5. 两端取数：
   - **前端**：从第 0 页翻到"页内出现 ≤ `TopId`（上次最新锚点）"= 与旧缓存接上；
   - **中间**：按 `lang_group` 游标吐缓存（不按页码切片，避免新帖位移错位）；
   - **底部**：`旧页码 + 新增条数/25` 估算，再用"该页 id 区间是否包含 `BottomId`"探页校验，
     最多 3 次；对不齐就作废连续区、纯网络；
6. 命中上屏前逐条刷新详情（每条 1 请求），后来改成"打开详情/下载时顺手回写"。

## 二、为什么停（按实际踩到的顺序）

### 1. 稳定性差，出现"内容丢失"

- 重进页面时显示的是**上次浏览末端**的内容：`BeginCacheSession()` 把网络游标抬到了
  `PagesCovered`（已连续覆盖的页），但那次缓存不可用（`Contiguous=false`）时游标没有重置，
  后续扫描直接从深层页码开始 →
  提交 `161b534` 才修掉（且只修了表象，机制本身仍脆弱）。
- "连续区 / 水位 / 位移 / 探页"四件事互相牵连：
  任何一处（`TopId` 没更新、`BottomId` 取了页首而不是页尾、探页落在边界）都会表现为
  **列表少一截 / 从中间开始 / 丢弃缓存**，而这些问题在 UI 上无法自动化验证，只能靠人眼发现。

### 2. 请求量并不占优

- 前端补抓的成本 = `ceil(新增帖数 / 25)` 页。全站（不只收藏作者）日更量大时，
  几百条新增就要十几页，**比"每个作者各拉第 0 页"更贵**；
- 首次进入命中 6 条时，原实现在最坏情况下要扫 8 页、还可能 0 命中；
- 后来加的"缺口估算 > 250 条就放弃"（`5fca827`）只是把最坏情况压到 1 页探测，
  但代价是"很久没来"时缓存直接作废 —— 复杂度换来的收益不稳定。

### 3. 概念负担与维护成本

需要同时维护：

- `PagesCovered`（连续覆盖页数）、`TopId / BottomId / BottomPageHint / Contiguous`（四个水位）；
- 页码位移估算 `EstimateBottomPage`、探页校验、作废与重建路径；
- 每处都要配"失败就纯网络"的兜底，逻辑分支呈指数增长。

对照之下，站点**本来就支持按作者查询**（`user=<id>` + `content=camouflage` → `get_user` 作者页），
绕开原生能力去做全局扫描，本质上是**用低命中率的查询模拟高命中率的查询** —— 这是根因。

### 4. 影响范围

- 这些复杂度侵入的是主列表的取数路径（`LoadNextPageAsync`），
  一旦出问题不只是这个功能不可用，**普通浏览也会受影响**（游标被污染）。

## 四、对照表

| 维度 | 本分支（全局 feed + 连续区，已停） | `master`（按作者，现行） |
|---|---|---|
| 查询 | 默认排序的全局 feed（`user=0`） | 每作者 `user=<id>`，`content=camouflage` |
| 命中率 | 低（取决于收藏作者在全局流中的密度） | 100% |
| 请求量 | `ceil(新增/25)` 页 + 探页 1~3 次 | 每作者 1 页 / 10 分钟；展示与深翻按需 |
| 定位方式 | 页码位移 + 探页校验 | 每作者 `MaxPostId` + `NextPage` |
| 失败模式 | 内容缺失 / 从末端开始 / 缓存作废重建 | 单作者失败只影响该作者，其余照常 |
| 影响面 | 侵入主列表取数路径 | 只在收藏作者模式内生效 |
| 代码量 | 约 900 行（含 4 个水位 + 对齐 + 作废） | 约 600 行（同步 + 归并） |

## 五、给未来的自己

1. **优先找站点的原生查询维度**，不要用"大范围拉取 + 本地过滤"去模拟它；
2. 缓存设计里最贵的是**定位**（页/游标/水位），能按"实体自身的游标"存就别算全局位置；
3. 任何"推断 + 校验 + 失败作废"的链路，都要先问：**失败时用户看到什么？**
   本方案的答案是"少一截"——这不可接受，所以停。
