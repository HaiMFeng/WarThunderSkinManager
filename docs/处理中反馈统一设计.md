# 处理中反馈统一设计

> **性质**：界面反馈机制的重构设计 —— 现状调查 + 目标设计 + 分阶段实施计划。
> 文中 `文件:行号` 截至撰写时（commit `5b549fc`，版本 0.2.0-dev）；重构会移动这些位置，以符号名为准。
> 落地完成后，规范部分并入 `界面设计规范.md` §2.6，功能描述并入 `软件功能设计.md`，本文保留为过程记录。

## 1. 目的与范围

**现状问题**：同一个程序里，等待反馈有 **5 种外观**；一次导入更会**先后出现 3 种**，且互斥完全靠编码纪律维持（§3.5）。

**目标**：为「阻断式等待」建立**唯一的复用容器** —— 样式统一、**不会同时叠加多个**、
按需决定**是否带进度条**，并把「互斥」由纪律变为机制。

**范围**：只统一**阻断式等待**（用户此刻做不了别的、就是在等）。
**不含**页内持续反馈：应用更新下载、WT Live 下载列表、部件表加载 —— 原因见 §4.4，它们并入全屏遮罩是**退化**。

## 2. 现状

### 2.1 五种形态

| # | 形态 | 实现 | 进度 | 可取消 | 模态 |
|---|---|---|---|---|---|
| A | 主窗口遮罩 + 加载圈 | `MainWindow.xaml:341-400`，由 `Services/Infrastructure/BusyIndicator.cs` 驱动 | 无 | 否 | 否（叠加层） |
| B | 独立进度窗口（导入） | `Views/ImportProgressWindow.xaml(.cs)` | 有 | **是** | **是**（`ShowDialog`） |
| C | 独立进度窗口（目录迁移） | `Views/MigrationProgressWindow.xaml(.cs)` | 有（按字节） | **是** | **是** |
| D | 页内 / 浮窗内联进度条 | `SettingsView.xaml:284`、`PartsView.xaml:190`、`SkinManagementView.xaml:160` | 有 / 不定态 | 部分 | 否 |
| E | 纯文字反馈 | 标题栏 `StatusText`（`MainWindow.xaml:59`）、按钮文案（`WTLiveImportWindow.xaml.cs:129`） | 无 | — | — |

另有 `Services/Infrastructure/AppBusy.cs`：**纯后台互斥锁，无 UI**，与以上 5 种都不是一回事。

### 2.2 一次导入为什么"交替闪烁"

`SkinsViewModel.RunImport` / `RunImportAsync` 的链路：

```
ImportProgressWindow(Loc["import.progressScanning"], total: 0)   // SkinsViewModel.cs:1564
    → total = 0 ⇒ BarVisible = false ⇒ 只有加载圈 + 文案
ImportPreviewWindow                                              // :1611（预览确认，非加载态）
ImportProgressWindow(Loc["import.progressCommitting"], count)    // :1624
    → 有计数 ⇒ 加载圈 + 进度条 + 可取消
BusyIndicator.Instance.Begin(Loc["busy.import"])                 // :1644
    → 加载圈 + 文案，无进度、不可取消（源清理 + 重建库）
```

一次操作看到的顺序是：**转圈窗 → 关闭 → 带条窗 → 关闭 → 转圈遮罩**。
三段提示三个容器，中间的窗口关闭与新建就是"交替"的来源。

## 3. 问题

不统一其实有 **4 个层面**，不止"窗口 vs 遮罩"：

### 3.1 容器两套
主窗口叠加层（A）与独立 `Window`（B/C）并存，二者的显示/隐藏、生命周期、Owner 规则完全不同。

### 3.2 进度条两套视觉
B/C 的进度条是**自绘**的 `Border + ScaleTransform`（`ImportProgressWindow.xaml:36-53`），
D 用的是**原生 `ProgressBar`**；而 `Themes/ThemeResources.xaml` 里**没有任何 `ProgressBar` 样式**
（全项目 `TargetType="ProgressBar"` 零命中）—— 即页内进度条走的是系统默认外观。

### 3.3 加载圈无法复用
那段 `Ellipse + StrokeDashArray + 旋转 Storyboard` 写死在 `MainWindow.xaml:376-394`，
**其他窗口拿不到** —— 想统一也无处可用。

### 3.4 取消语义各不相同
- B/C：取消 = **关闭窗口**（`Closing` 钩子触发 CTS，`ImportProgressWindow.xaml.cs:47`）；
- A：**没有**取消；
- D：取消是卡片上的按钮。

### 3.5 互斥靠纪律，规范里留着"疤"

`界面设计规范.md:155-156` 明确写着：

> 遮罩范围**不得包含模态窗**（属性页 / 确认框）：`using` 范围要止于弹窗之前，
> 否则遮罩会一直罩在弹窗后面的主窗口上。

这条规范本身就是缺陷的证据 —— 遮罩是**主窗口叠加层**，一旦有模态窗起来，遮罩就成了罩在弹窗后面的鬼影。
代码里到处是维持顺序的注释纪律（`SkinsViewModel.cs:799-800`、`:847-848`、`:1642-1644`）。
**互斥靠人记，不靠机制**，这是重构最值得修的一点。

### 3.6 硬约束：取消入口不可被挡

`MainViewModel.cs:1726-1728` 记着实测教训：

> 下载阶段**不能开全屏遮罩**：下载可能持续几分钟，遮罩会挡住卡片上的「取消下载」按钮
> （实测踩过：取消入口完全不可达）。

**「能取消」是长操作的一等需求。** 统一容器若只有"加载圈 + 文案"，必然重演此坑；
所以容器必须能表达取消入口，否则应用更新这类场景永远无法归并。

## 4. 目标设计

### 4.1 容器能力

单一容器，四种可组合状态：

| 状态 | 组成 |
|---|---|
| 阻塞 + 不定态 | 压暗底 + 卡片 + 加载圈 + 文案（现有 A 的全部行为） |
| 阻塞 + 确定态 | 再加进度条与计数/百分比文案 |
| 阻塞 + 可取消 | 卡片内出现取消按钮（取消入口**始终可点**，见 §3.6） |
| 仅文案 | 无加载圈（用于瞬时切换的短阶段，避免图标闪动） |

规则：

- **进度与取消由最外层作用域决定**；内层的进度设置被忽略（避免嵌套时进度跳变）——与现有"文案取最外层"一致；
- **无总量时自动退化为不定态**（不显示进度条），沿用 `ImportProgressWindow.xaml.cs:43` 的既有判据；
- 计数归零时，文案 / 进度 / 取消回调整体重置。

### 4.2 互斥与嵌套

- 容器**全局唯一**，可见性由引用计数驱动 —— 天然不可能同时叠加两个提示；
- 保留 `BusyIndicator` 现有的嵌套语义（`using` + 计数 + 幂等 Dispose + 文案取最外层，`BusyIndicator.cs:43-86`）；
- 遮罩出现/消失**不做延时**（`界面设计规范.md:154` 已定：这些操作本就 1 秒以上，立即可见更重要）。

### 4.3 视觉

**沿用** `界面设计规范.md:137-156` 已定的遮罩观感，不重新设计：
压暗底（主题背景 + `Opacity=0.72`）+ 居中卡片（圆角 10 / 轻投影 / `Padding=22,16`）+ 实心弧加载圈（18 / 描边 2 / 1.1 秒一圈）+ 一行文案。
改动点只有一处：把加载圈与进度条**下沉到主题**，使任何窗口都能复用，并让四套主题自动一致。

### 4.4 为什么页内反馈不并入

| 场景 | 为什么不并入全屏遮罩 |
|---|---|
| 应用更新下载 | 持续数分钟，**必须保留取消入口**（§3.6），全屏遮罩会挡住它 |
| WT Live 下载列表 | **多个任务可并行**，遮罩会挡住列表本身与各行的重试/取消 |
| 部件表加载 | 页面内的局部反馈，遮罩属于过度反应 |

把这三处塞进全屏遮罩是**退化**。因此统一边界是 **A + B + C**，不包括 D。

## 5. 分阶段实施

| 阶段 | 内容 | 行为变化 | 风险 |
|---|---|---|---|
| **1. 容器成型** | 遮罩抽成可复用控件；加载圈与 `ProgressBar` 样式下沉主题；`BusyIndicator` 增加进度与取消能力（新增能力由自检覆盖，业务调用点暂不动） | **无**（视觉与语义与现在一致） | 低 |
| **2. 迁移模态进度窗** | 导入 3 个调用点（`SkinsViewModel.cs:1564/1624/1757`）与目录迁移 1 个（`MainViewModel.cs:437`）改用统一容器；删除 2 个窗口 + 2 个 VM；补并发闸门 | **有**：模态 → 非模态 | 中高 |
| **3. 收敛特例** | 评估目录迁移的特殊语义（迁移中是否允许操作）；按结果决定是否保留独立形态 | 视评估 | 中 |

阶段 1 只铺路：不改任何调用点，因此可以独立验证与回滚。

## 6. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **模态语义丢失**（最高） | B/C 现在用 `ShowDialog`，既阻塞调用线程也**阻止用户操作主界面**；改为叠加层后，用户能在导入/迁移进行中切页面甚至触发别的操作。这是**行为变化**，不是纯重构 | 沿用项目已有的闸门模式（`MainViewModel.cs:1724` 的 `IsMaintenance` / `SettingsEnabled`），把"操作期间禁止的危险入口"显式列出并遮蔽 |
| **取消入口**（中高） | 见 §3.6 | 容器提供常驻可点的取消按钮；迁移后逐个场景验证"取消始终可点" |
| **目录迁移的特例**（中） | 迁移会**搬动数据目录**，期间允许操作是否安全需单独确认（`AppBusy` 正是为它加的互斥：`BlobGc.cs:120`、`LibraryService.cs:262` 见忙即让） | 阶段 3 单独评估，必要时保留独立形态而不强行统一 |
| **自检覆盖**（中） | `Dev/SelfTest.cs:1573-1587` 已断言计数的嵌套与幂等 | 扩展覆盖进度与取消；保持既有断言不回归 |
| **视觉回归**（低） | 抽取控件时容易丢细节（描边宽、卡片内边距、动画时长） | 阶段 1 以"行为不变"为验收线，真机对比 |

## 7. 验收判据

- 导入全程只出现**一个**加载容器，不再有窗口开关造成的交替；
- 任何时刻不存在**两个**加载提示同时可见；
- 进度条外观与页内进度条**同源**（同一主题样式，四套主题一致）；
- 凡支持取消的操作，取消按钮在遮罩可见期间**始终可点**（§3.6）；
- 构建 0 error / 0 warning、自检异常 0，既有 `BusyIndicator` 嵌套与幂等断言不回归；
- 删掉的实现确实不再被引用（2 窗口 + 2 VM），文档 `界面设计规范.md` §2.6 同步更新。
