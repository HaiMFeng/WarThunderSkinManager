# 软件功能设计（WarThunderSkinManager）

> 目标：管理《战争雷霆》`UserSkins` 下的自定义皮肤。
> 本文档整理自需求讨论，仅描述**功能与设计方向**，不含代码实现。
> 配套格式规范见 `docs/涂装文件结构与BLK格式参考.md`。

---

## 1. 概述与痛点

软件管理 `UserSkins` 下的皮肤，重点解决两个问题：

1. **目录堆积导致扫描慢/崩溃**：实际往往只有几十个载具，但一个载具有很多皮肤，全部 blk/贴图堆在一个文件夹，游戏扫描缓慢甚至崩溃。
2. **同载具皮肤部件不齐**：例如载具 A，一个皮肤做了导弹贴图适配，另一个只做了主体，导致外观/完整性不一致。

核心能力：导入并解构涂装 → 存入资源库 → 按载具组织 → 贴图适配（用户选择）与 `blk` 动态重写 → 以"热重载友好"的方式输出到游戏 `UserSkins/WTSM`。

---

## 2. 核心机制与三个目录

### 2.1 三个核心目录（均由用户指定/确认）

| 目录 | 指定方式 | 作用 | 规模 |
|------|----------|------|------|
| **游戏 `UserSkins` 目录** | 用户**手动指定** | 程序在其下建立 `WTSM/` 子目录作为激活输出；`WTSM` 之外可由一键导入扫描 | 小 |
| **程序资源存储目录** | 用户**手动指定**（必须） | 皮肤库：存储**所有**涂装文件（解构/导入后的原始数据） | 可能**几百 GB**，务必手动选 |
| **程序配置目录** | 一般**默认位置**，用户也可改 | 语言、配置、映射文件、预览图缓存等小文件 | 小 |

> 程序只管理 `<UserSkins>/WTSM/`；`WTSM` 之外的其他文件夹视为用户自行放置、未受管理的涂装，可供一键导入扫描。

### 2.2 游戏 UserSkins 目录结构（激活输出）

```
<UserSkins>/
└── WTSM/                       // 程序管理的激活输出根（便于区分、看着干净）
     └── <载具标识>/
          └── <载具标识>.blk    // 一个载具一套 blk，文件名 = 内部标识
          └── *.dds / *.tga     // 该载具当前激活使用的贴图
```

- **一个载具 = 一个 blk 文件**（文件名即内部标识，见格式文档 §3）。
- `WTSM/` 由程序维护，用户不在游戏内手动改。

### 2.3 热重载原理（关键）

只要不改 blk 的**文件名和路径**，只改变 blk 的**内容和相关贴图文件**，游戏会将其识别为同一套涂装并**热重载**，用户无需在游戏内重新选择涂装。

因此程序的工作方式：根据用户选择，**动态重写 blk 内容 + 移动/复制贴图文件**到对应 `<UserSkins>/WTSM/<载具标识>/`，而非让用户手动管理 `UserSkins`。

## 3. 功能模块

### 3.1 导入涂装

支持多种来源，导入后统一进入"解构"流程（§3.2）：

- **从 `UserSkins` 一键导入**：扫描 `<UserSkins>` 下 **`WTSM` 之外**的其他文件夹（即用户自行放置、未受管理的涂装），自动解构并纳入资源存储目录。
- **导入后清理源**（导入预览里可勾选，默认勾选）：
  - **从 `UserSkins` 一键导入**：只删除本次**成功导入**的 blk 所在的**顶层子文件夹**；直接躺在根下的 blk 只删该文件（不影响 `UserSkins` 根目录本身）。
  - **导入文件夹**：整个源文件夹都是本次导入的来源 → **删除该文件夹本身**。
  - **安全规则**：只要某个位置还有**导入失败**的 blk，就**跳过**清理该处，并在状态栏提示跳过数量，避免连同失败的数据一起删掉。
  - `WTSM`（程序自己的输出）永远不删除。
  - 涂装已完整入库，随时可用「导出」（§3.11）恢复原始模组，因此清理是安全的；否则这些原始文件夹会继续留在 `UserSkins` 里让游戏扫描，等于没解决痛点。
- **拖入涂装文件夹 / 压缩包**：把文件夹或压缩包（可一次拖多个）拖到**程序窗口任意位置**即可导入，拖拽时窗口显示提示浮层。
  - 只拖入**一个文件夹** → 等同「导入文件夹」（可勾选删除该文件夹）；
  - 含压缩包、或一次拖入多项 → 逐个解压后合并到**同一个导入预览**里确认。

**压缩包处理**：
- **压缩库选型：SharpCompress**（.NET 生态常用多格式库，支持 zip / 7z / rar / tar / gzip / bzip2 等读取，兼容性优先、覆盖常见格式）。
- **加密压缩包**：遇到受密码保护的压缩包（如带密码的 zip / 7z）时，程序**弹出密码输入框**；密码不对可**重试**（最多 3 次），取消则**跳过该压缩包**（不影响同批其他来源）。
- 流程：**先解压到程序资源存储目录下的暂存区** `<资源目录>/imports/extract/<随机>`，再从解压结果中**解构**涂装；暂存目录在流程结束后**自动清理**（贴图已按内容寻址入库，解压产物只是中间物，不在用户磁盘留渣）。
- 解压后可选项：**「导入成功后删除压缩包」**（在导入预览对话框里勾选，默认**不勾**——压缩包是用户下载的原件，勾选才删）。
- **建议包名**：压缩包文件名（去扩展名）；包内只有**一个顶层文件夹**时取该文件夹名。

**导入选项记忆**：
- 导入预览里的勾选（「导入后删除源文件夹」/「导入成功后删除压缩包」）**会被记住**，下次以**同样方式**导入时默认沿用。
- 记忆**按导入方式分开**（一键导入 UserSkins / 导入文件夹 / 压缩包）——三者的清理语义不同（UserSkins 只删贡献了导入的顶层子文件夹，导入文件夹删整个源文件夹）。
- 存在 `config.json`（`importDeleteSourceUserSkins` / `importDeleteSourceFolder` / `importDeleteArchive`）；出厂默认为「删除源 = 勾」「删除压缩包 = 不勾」。
- 取消导入预览时**不记录**（用户未做选择）。

**涂装包命名（导入时）**：
- 目的：让用户在**选择部件贴图**时能区分「这张贴图来自哪个模组」，避免同一载具多包难以辨别。
- **自动建议名来源优先级**：**压缩包文件名**（去扩展名；包内仅一个顶层文件夹则取其名）→ **blk 所在文件夹名**。
  - **不使用 blk 文件名**作包名：同一载具的 blk 名恒等于载具标识，无区分意义。
- **名称清洗**：去非法路径字符、折叠空白、限长；无论是否改名，均保留 `SourceImportId` 溯源。
- **允许重名**：不做自动唯一化（内部 Id 为 GUID，不受影响），用户可自行改名。
- **同组改名（导入预览里）**：**建议名相同**的条目 → **归为一组**，改一次**组名**即同步到组内所有条目。
  建议名相同的含义就是「来自**同一压缩包**或**同名文件夹**」——同一个模组常含多个载具的 blk，一次改名即可覆盖整套模组。组内单个条目之后仍可在涂装包属性界面（§3.6）单独改名；只有单条目的组不显示组头，直接在该行改名。

**导入预览确认（导入前）**：
- 导入前弹出预览对话框，列出将导入的涂装包：**载具标识 / 建议名（可编辑）/ blk 路径 / 贴图条目数 / 缺失贴图数 / 校验告警**（告警单元格可悬停查看明细）。
- 用户可逐个改名后再确认；**确认后才真正解构落盘**。
- **分组**：建议名相同（= 同一压缩包 / 同名文件夹）的条目会归为一组并显示组头（`N 个包` + 组名 + 来源目录），**改组名即同步组内全部**；单条目组不显示组头，直接在该行改名。
- 便于在导入前就发现贴图缺失、`from` 缺 `*` 等问题（格式文档 §9 / §10）。
- **贴图缺失属于校验失败**：`to` 指向的贴图在 blk 同目录找不到的条目会被标记（精确名优先，回退大小写不敏感匹配），该部位在该包中视为**无贴图**，**不会写入 blk**。

### 3.2 解构涂装

- 递归识别 blk 文件（任意层级嵌套，见格式文档 §2），以 **blk 所在目录**为贴图查找根。
- 解析 blk 内容：`replace_tex` / `set_tex` 条目（`from` 模块代码、`to` 贴图名、`param`、`*` 通配符等）。
- 收集同目录贴图文件，形成"涂装包"的初始数据，存入资源存储目录。
- **贴图校验（关键）**：每条 `replace_tex` / `set_tex` 的 `to` 必须能在 blk 同目录解析到（精确名优先，回退大小写不敏感匹配）。
  - 找不到 → 该条目标记为**贴图缺失**：不进入资源库的贴图引用、不作为可选项、也**不参与输出**；界面上该部位显示为「无」。

### 3.3 载具识别与结构推导

- 从 blk **文件名**获取**载具内部标识**（如 `f_15a`）。
- 从 blk 内容的 **`from` 字段**推导该载具"可以有的结构"（各部件/位置）。
  - 注意：模块代码命名是**经验总结、非官方规范**，Gaijin 命名不统一（见格式文档 §6），解析时**不能硬性依赖前缀/后缀判定**，以 blk 实际值为准。
  - 载具中**显示的即 `from` 字段名本身**，**暂时不加入具体部位的翻译解析**（即不做"body → 车体"这类映射）。

### 3.4 涂装包管理（程序内部核心组织）

层级关系：

```
国家 → 载具 → 涂装包
```

- **涂装包**：导入时的一个 blk 默认作为一个涂装包；包含该载具各部件的具体贴图。
- 一个载具可包含多个涂装包（即"一个载具有很多皮肤"）。
- 用户操作：
  - **复制**现有涂装包（基于已有包派生新组合）。
  - **替换部件贴图**：选择某部件（按 `from` 字段定位），用已有的其他**同部件**贴图替换（匹配规则见 §3.5）。
- 涂装包属性（见 §3.6）。

**国家层级来源（自动分类规则）**：
- 内部标识**有可识别国家前缀**的（如 `cn_vt5` 中国、`us_*` 美国等），按前缀**自动归类**。
- **没有具体前缀**的（如 `f_15a`），归入**「未分类」**，由用户在载具管理界面（§3.10）移动到对应国家。
- 用户手动指定的国家**持久化**到 `<配置目录>/mappings/vehicle_countries.json`，并**优先于**前缀自动归类。

**涂装管理界面布局（三级导航）**：
- **顶端横条**：切换国家（含「全部」；显示各国载具数，仅显示有载具的国家）。
- **左侧二级列表**（主导航右侧）：切换当前国家下的载具；显示名取自映射文件（§3.7），未映射时回退内部标识。
- **右侧内容区**：选中载具的**涂装包卡片网格**——缩略图 + 底部半透明名称条；卡片尺寸与列数**随窗口自适应**，可**拖动排序**（顺序持久化到各包 `meta.order`）。已激活的包在卡片上有标记。
  - 卡片右键菜单：**激活为当前涂装** / 取消激活 / 编辑（属性）/ 复制 / 导出 / 删除。
- **本页还负责**：**激活某一套涂装包**（每个载具同时只激活一套，§3.8）与**同步输出**；而"每个部件用哪张贴图"是**涂装包自身的属性**，在**涂装包属性界面**（§3.6）里配置。
- 即：**涂装管理界面 = 涂装包管理 + 激活 + 同步**；**载具管理界面（§3.10）只负责载具显示数据**（显示名、国家、只读结构）。

### 3.5 贴图适配与 blk 重写（用户手动选择）

- **问题**：同载具的不同皮肤部件贴图不齐。例：皮肤甲有导弹贴图，皮肤乙只有主体（无导弹）。
- **部件匹配规则（关键）**：以原始 blk 中的 **`from` 字段**为准；**相同 `from` 字段即视为同一位置贴图**。
- **能力（由用户自行选择，非自动）**：用户在同载具的多个涂装包中，**手动选择**某个来源包，将其含有、而目标包缺失（或想替换）的某部件贴图（按相同 `from` 字段匹配）合并进目标 blk；程序据此把对应 blk 条目与贴图文件写入目标 blk，并复制/引用相应贴图文件。
- **结果**：用户确认后，目标 blk 重写、也"适配了导弹"，且因 blk 文件名/路径不变，游戏热重载生效。
- 这是对 §2.3 热重载机制的直接应用：适配 = 用户选择 + 重写 blk 内容 + 调度贴图。
- **界面位置**：**涂装包属性界面**（§3.6）中的「部件贴图」区——"用什么贴图"是**涂装包自身的属性**。
  - 部件以 `from` 为行（相同 `from` = 同一位置），每行一个下拉选择候选贴图；候选来自**同载具所有涂装包中相同 `from`** 且**贴图可用**的条目（并显示来源包名以便分辨），另含「**无**」选项（该部件在本包中不输出，游戏用默认贴图）。
  - **贴图缺失的条目既不作候选、也不写进 blk**；某部位若没有任何可用贴图，该行只显示「无」。
- 保存结果写入该包 `<资源目录>/packages/<包Id>/meta.json` 的 `parts`（完整快照，见 §6.5）。
- **激活与输出**：用户在涂装管理界面**激活该包**后同步（§3.8），程序按该包的 `parts` 生成 blk 与贴图 → 热重载生效。
- **派生新组合**：复制现有包（§3.4）→ 在属性界面替换若干部件贴图，即得到一套新的组合。

### 3.6 涂装包属性（显示名 / 预览图 / 部件贴图）

- 每个**涂装包**可配置：
  - **自定义显示名**（默认名来自导入时的自动建议，见 §3.1；允许重名）。
  - **预览图**：
    - 格式：**png**。
    - 来源：**选择文件** 或 **从剪贴板导入**。
    - 无预览时使用**空白占位图**（样式后续具体开发时再替换）。
  - **部件贴图**（§3.5）：逐部件 `from` 选择**本包**使用的贴图；候选 = 同载具所有包中相同 `from` 的**可用**贴图（已排除贴图缺失条目，含本包自身），另含「**无**（不输出该部件）」。下拉项只显示「包名 · 贴图名」，**不含写入方式**。
    - **写入方式滑块**：每行右侧一个 `replace_tex` ⇄ `set_tex` 滑块，决定该部件写入 blk 的方式（§6.2）。初值**跟随所选贴图在来源 blk 中的写法**，用户可覆盖；部件选「无」时滑块不可用（该部件不输出）。
    - **推测标签**：部件名右侧最多显示三个标签（按优先级）：**① 武器 / 导弹**（红色，来自内置武器表）→ **② 部位 / 功能** → **③ 贴图类型**。
      例：`vt_5_body_c` → 「主体」「法线」；`su_r_77_1_missile_c` → 「武器 / 导弹」「法线」；`88mm_flak41_c` → 「武器 / 导弹」「高射炮」「法线」。
      - **武器 / 导弹识别**（红色标签，规则明确、非推测）：见下方「武器名表」。
      - **部位 / 功能 + 贴图类型**：依据 = 格式文档 §6 的「部件前缀 + 贴图类型后缀」规律（`_n` 纹理、`_c/_a` 法线、`_ao` 环境遮蔽、`_dmg` 受损；`body/turret/gun/mount/track/cockpit/camo/…`），部件词可带尾随编号（`pylon1` ≈ `pylon`）。贴图类型标签带色调（**纹理绿 / 法线黄**，见界面设计规范 §5.10），便于在部件列表里快速区分。
        **主体**：两种情形都标「**主体**」——① **飞机等**：`from` 以该载具标识开头、且**其后只剩贴图类型后缀**（载具 `su_30mkk` 的 `su_30mkk_c` / `su_30mkk_n` / `su_30mkk_c_dmg`）；② **地面 / 水面载具**：名字里带部件词 `body`（如 `vt_5_body_c`），即车体 / 船身。
        ⚠️ ① 不能只看后缀——绝大多数部件贴图同样以 `_c` / `_n` 结尾（如 `su_30mkk_pylon1_n`、`vt_5_gun_c`），所以标识之后必须**整段就是类型后缀**，多一个词（哪怕只是编号）都不算主体。
      - **仅供人工识别参考**：命名是社区经验总结、非官方规范，识别不出时不显示标签，程序**绝不**据此改动数据。
    - **武器名表**（内置 `Assets/units_weaponry.csv` 嵌入资源，全量武器译名表；可用 `<配置目录>/ref/units_weaponry.csv` 覆盖，见下）：
      - **预处理**：只取首列 ID（不解析译文列）→ 取「类别之后的**第一段**」作为名字（`weapons/su_r_73e_default/short` → `su_r_73e`）→ 去掉 `_default` / `_user_cannon` 等尾部标记 → **去掉分隔符与下划线**并转小写（`su_r_73e` → `sur73e`）；同时登记「去掉首个前缀段」的形态，好让表里的 `cn_pl12` 也能命中部件 `pl12_missile_c`。
      - **匹配**：把部件 `from` 去掉贴图类型后缀（`_c` / `_n` / `_c_dmg`…），再从尾部**最多丢掉 3 段**部件词（`_missile`、`_rail`…）后逐级查表，任一级命中即显示红色「**武器 / 导弹**」。
      - **类别过滤**：只采纳 `weapons/…` 与**无类别的裸 ID**（如 `su_r_73`、`128mm_pzgr_ts`）；`explosiveType` / `modification` / `sonicDamage` / `weapons_types` 等经查是参数、改装件、角度阈值，不是武器，忽略。
      - 命中武器时，不再重复显示命名推测出的「导弹 / 炸弹 / 火箭弹 / 发射架 / 鱼雷」标签（武器表更权威）。
      - **可单独替换**（与载具译名表同一机制，见 §3.7）：`<配置目录>/ref/units_weaponry.csv` 存在时**优先于内置表**，替换后**立即生效**（无需重启）；设置页可「导出内置表」作为更新起点。
    - **首次使用滑块会弹窗**说明两者区别（`set_tex` 会一并写入 `param:t="camo_skin_tex"`，一般只用于车体/机体的迷彩主贴图；写错不会报错但涂装可能不生效）：
      **取消 → 本次不做任何改动、滑块回滚，下次尝试仍会提示；确认 → 之后不再提示**（确认状态记录在 `config.json` 的 `replaceSetNoticeSeen`）。
    - 保存即写入该包 `meta.json` 的 `parts`（完整快照，含每条的 `mode`）；未配置过时沿用导入的 `source.blk` 原始条目。
    - 这是「复制涂装包派生新组合」（§3.4）的落地方式：复制一个包 → 在属性界面替换几个部件 → 得到新的组合。
- **预览图缓存**：
  - 缓存键**跟随涂装包**（如 `previews/<packageId>.png`）。
  - 读取时若缓存**失效/缺失** → 显示**空白占位图**（默认本身也是空白图）。

### 3.7 载具标识映射与自动译名

**显示名解析优先级**：

1. **用户映射**（`<配置目录>/mappings/vehicles.json`）——用户显式改过的名字；
2. **内置译名表**（见下）——按**当前界面语言**自动查表得到的官方译名；
3. **内部标识**本身（`f_15a` 这种原始标识）。

**用户映射（`mappings/vehicles.json`）**：

- **内部标识**（即 blk 文件名，如 `f_15a`）玩家可自定义**显示名**（如"F-15A 鹰"）。
- 映射关系保存在**一个文件**中：`内部标识 ↔ 载具名字`；位于**程序配置目录**下（见 §4），格式 **JSON**。
- 支持：**导出 / 导入 / 合并**。
- **合并冲突策略**：导入/合并遇到相同内部标识的冲突 key 时，**逐个弹窗让用户选择保留哪个**（来源值或现有值）。
- 只保存**用户改过的**条目：把自定义名清空、或改回内置译名，该条目会从文件里移除，重新回落自动译名。

**译名表（内置 `Assets/units.csv` 嵌入资源随程序发布；可用 `<配置目录>/ref/units.csv` 覆盖）**：

- 内容：**内部标识 → 各语言译名**，一行含 `English / French / Italian / German / Spanish / Russian / Polish / Czech / Turkish / Chinese / Japanese / Portuguese / Ukrainian / Serbian / Hungarian / Korean / Belarusian / Romanian / TChinese / HChinese / Vietnamese` 等列。
- 格式：无 BOM 的 **UTF-8**、字段分隔符 `;`、字段用双引号包裹；第一列为 `<ID|readonly|noverify>`。
- **同一载具有多条词条**（以 `f_15e` 为例）：
  | 词条 | 含义 | 例（Chinese） |
  |------|------|----------------|
  | **`f_15e_1`** | **短名**（本程序采用——长度合适，适合界面显示） | `F-15E` |
  | `f_15e_0` | 全名（带绰号 / 型号后缀，偏长） | `F-15E 攻击鹰` |
  | `f_15e_2` | 类型 / 类别 | `战斗机` |
  | `f_15e_shop` | 商店名 | `F-15E` |
- **自动查表顺序**：短名 `<标识>_1` → 全名 `<标识>_0` → 标识本身 → 商店名 `<标识>_shop`。
  直接以 `_1` 结尾命名的 blk（如 `f_15e_1`）也能直接命中。
- **自动识别**：导入（或刷新库）时按**当前界面语言**取译名——`zh-CN` → `<Chinese>`、`zh-TW` / `zh-HK` → `<TChinese>`，其他语言按语言主标签（`en` → `<English>` …），该语言列缺失时回落 `<English>`；表中查不到则回落到内部标识。
- **读取时的字符清理**：源表里混了两类「非文本」字符，读取时按类别处理：

  | 类别 | 例 | 处理 | 原因 |
  |------|----|------|------|
  | **国旗占位符** | `▄`(U+2584)、`◔`(U+25D4)、`␗`(U+2417)、`☢`(U+2622)、私用区 `U+F059` … | **替换为空格**（随后折叠空白） | 游戏在自定义字库里把它们画成「该载具隶属某国」的小国旗，其他字体下就是乱码；改成空格可避免把前后单词粘连 |
  | **不可见字符** | 零宽空格 U+200B（源表在 CJK 之间夹了大量）、变体选择符、方向控制符 | **直接删除** | 保留会把词拆开（`四[ZWSP]联[ZWSP]机`），且影响复制/比较 |

  覆盖范围：控制图形 `U+2400–243F`、制表符 `U+2500–257F`、块元素 `U+2580–259F`、几何图形 `U+25A0–25FF`、杂项符号与装饰 `U+2600–27BF`、`U+2B00–2BFF`、私用区 `U+E000–F8FF`。
  **不影响**正常文本：弯引号 `U+201C/201D`、`№`、全角括号、`°` 等一律保留。
- **可单独替换更新**（与武器名表 §3.6 同一机制，由 `DataTables` 统一处理）：
  - **首次启动即写出**：把内置表写到 `<配置目录>/ref/`（`units.csv` / `units_weaponry.csv`），用户可直接编辑；两处内容一致，用户不关心也能照常使用。
  - **用户表优先，内置表兜底**：用户表存在 → 用它；删掉该文件即回落内置表。
  - **替换后立即生效**（无需重启）：按「用户表路径 + 最后写入时间」判断缓存是否过期并重建。
  - **跟随程序更新**（与语言文件 §3.9 同一思路，按**基线** `<配置目录>/ref/_units.defaults.csv` 等判断）：
    - 用户表与基线**相同**（= 用户没改过）+ 程序内置表更新 → **用新版内置表覆盖**，新载具/改进译名自动生效；
    - 与基线**不同**（= 用户改过）→ **保留用户表**，不覆盖；
    - 基线缺失（从旧版本升级上来）→ 保守保留用户表。
  - 设置页提供两个按钮：**「打开」**（目录不存在则创建、表缺失则先写出默认表，再打开资源管理器）与**「导出内置表」**（把当前内置表覆盖写到该目录，用于改坏后恢复或重新取一份基准）。
  - 未放用户表时，程序随版本更新即可获得新载具 / 改进译名；**用户自定义名**（`mappings/vehicles.json`）始终优先于译名表。

### 3.8 动态同步到 UserSkins/WTSM（激活输出）

- 用户完成选择（国家 → 载具 → **激活某一套涂装包**）后，程序将结果写入 `<UserSkins>/WTSM/<载具标识>/`。
- **界面位置**：**涂装管理界面**（§3.4）。在涂装包卡片上**激活**该包（每个载具同时只激活一套），**「同步此载具」**输出当前载具，**「同步所有」**输出库中所有已激活的载具。
- **激活即同步**：右键**激活**一套涂装包时，程序**立即同步该载具**（等价于随手点了「同步此载具」）——激活是明确要输出这套包，不该还要再点一次；此路径**不受自动同步开关与缓冲时间影响**（游戏热重载随即生效）。状态栏给出「已激活「包名」；已同步：N 条映射、写入 M 张贴图」。
- **输出内容** = 该**激活包的部件贴图配置**（§3.6 的 `parts`）：每个部件写出一条 `replace_tex` / `set_tex`；未设置部件不输出（游戏用默认贴图）。
- **贴图缺失的部件不写入 blk**（§3.2 校验的直接结果）：宁可不写，也不写一条指向不存在贴图的条目——游戏不报错但会**静默失败**。被跳过的部件会在同步报告的告警里列出。
- **同步触发时机**（兼顾性能，避免随意切换频繁读写）：
  - **「同步所有」按钮**：用户随时手动点击，立即将当前所有选择写入 `WTSM`。
  - **自动更新（可选，设置开关）**：开启后，用户**停止操作达「缓冲时间」**再自动同步（而非每次切换都写盘）。
  - **设置项**：自动更新开关、缓冲时间（秒）。
  - **短缓冲提醒**：缓冲时间阈值设为 **2 秒**；若用户将缓冲时间设得低于 2s，弹窗提醒可能影响性能/导致频繁读写。

### 3.9 国际化（语言文件）

- 程序所有**文字资源使用语言文件**，可替换。
- 语言文件位于**程序配置目录**下（见 §4），格式 **JSON**，按功能分子目录，便于后续扩展多语言、避免硬编码界面文案。
- **内置文案更新**：语言文件旁维护一个**基线文件** `lang/_<culture>.defaults.json`（记录**上一次的内置默认值**），据此区分「用户改过的条目」与「只是旧版内置文案」：
  - 文件里的值与基线**相同** → 用户没改过 → 采用程序内置的**新版文案**（内置文案改版后自动生效，无需手动清理）；
  - 与基线**不同** → 用户自己改过 → **保留用户值**，不被覆盖；
  - 基线缺失（本机制引入之前生成的文件）→ **保守处理**：保留文件里的值，不覆盖用户改动。
- 程序新增的 key 会以内置默认**自动补齐并回写**语言文件（见 §4）。

### 3.10 载具管理界面（只配置载具显示数据）

- 提供独立的**载具管理界面**，用于**配置/展示载具的显示数据**：内部标识（blk 文件名）、显示名（映射文件 §3.7）、国家、涂装包数量、各 `from` 结构（只读）。
- 用户可在此**手动配置国家**：通过**下拉框**选择（含「未分类」及各国列表），把「未分类」载具移动到对应国家；结果写入 `<配置目录>/mappings/vehicle_countries.json`，**优先于**前缀自动归类（§3.4）。
- 也可在此编辑**显示名**（写入 `mappings/vehicles.json`）等元数据；改动即时自动保存。
- 各 `from` 结构仅**只读展示**，用于了解该载具有哪些部件位置。
- **本界面不含**部件贴图适配与同步输出——这两项在**涂装管理界面**（§3.4 / §3.5 / §3.8）。

### 3.11 导出 / 恢复原始模组
- 每个涂装包保留 `source.blk`（原始 blk）与 `meta.json`（含 `to → blob` 映射、原名），见 §6.5。
- 导出某涂装包为原始模组文件夹：将 `source.blk` 作为 `<载具Id>.blk`，并按 `meta.textures` 把对应 blob **重命名回原名（`to`）** 复制到目标文件夹。
- 因复制包只是多一份索引（§6.5），各包可独立导出、互不干扰，恢复出的目录结构与导入时一致。

### 3.12 数据清除（危险操作）

- 设置页提供**「清除所有数据」**入口，用于清空本程序累积的数据后重新测试。
- **三重确认**（缺一不可）：
  1. **警告弹窗**：说明不可恢复、建议先备份；
  2. **清除面板**：展示各范围的**路径与规模统计**，由用户**勾选**要清除的范围，并需**输入确认词 `DELETE`** 才会启用清除按钮；
  3. **最后确认弹窗**：列出将要删除的范围。
- **可勾选的范围**（彼此独立）：

  | 范围 | 内容 |
  |------|------|
  | 资源库数据 | `<资源目录>/packages`、`blobs`、`imports` |
  | 配置数据 | `<配置目录>/mappings`、`loadouts`、`previews` |
  | 语言文件与程序配置 | `<配置目录>/lang`、`config.json`（会丢失目录设置与自定义文案，建议清除后重启程序） |
  | 游戏输出目录 | `<UserSkins>/WTSM` |

- **安全边界**：只删除程序自己管理的子目录/文件；**绝不触碰** `UserSkins` 中未受管理的涂装，也不会删除 `UserSkins` / 资源目录本身。

## 4. 目录结构约定

```
<UserSkins>/                  // 游戏 UserSkins 目录（用户手动指定）
└── WTSM/                     // 程序管理的激活输出根
     └── <载具标识>/
          └── <载具标识>.blk
          └── *.dds / *.tga

<资源存储目录>/               // 程序资源存储目录（用户手动指定，可能几百G，皮肤库）
├── blobs/                   // 贴图内容寻址存储（去重核心）：<sha256>.<ext>
└── packages/<PackageId>/    // 包稳定标识(GUID)；与 国家/载具 完全解耦
     ├── source.blk          // 导入时的原始 blk（保留溯源，程序不重写）
     └── meta.json           // 包元数据（含同载具内 order 排序）+ textures:[{to, blob}] 引用
（国家/载具仅存于配置目录索引，物理上不建对应目录 → 国家改名零成本）

<配置目录>/                   // 程序配置目录（默认位置，可选改）
├── lang/                     // 语言文件（JSON），如 zh-CN.json / en-US.json
│                             //   内部基线文件 _zh-CN.defaults.json（§3.9，用于内置文案更新）
├── mappings/                 // 载具标识 ↔ 显示名（vehicles.json）
│                             //   载具 → 国家（vehicle_countries.json，用户手动归类）
├── loadouts/<载具Id>.json    // 该载具激活的涂装包（{ activePackageId }，见 §6.3）
├── config.json               // 程序配置（含三个目录路径、同步设置、语言、导入选项记忆等）
├── ref/                      // 可单独替换的数据表：units.csv（载具译名）/ units_weaponry.csv（武器名表）
│                             //   首次启动自动写出；改过的优先，未改过的随程序更新（§3.6 / §3.7）
│                             //   内部基线 _units.defaults.csv / _units_weaponry.defaults.csv（判断是否被改过）
└── previews/                 // 预览图缓存（png，键=涂装包 id）
```

**小文件格式选择（JSON）**：
- 配置、映射、语言文件统一采用 **JSON**——通用、人类可读、`.NET` 原生支持（`System.Text.Json`）、便于程序化导出/导入/合并。
- 语言文件示例：
  ```json
  { "ui.import": "导入", "ui.vehicle": "载具" }
  ```
- 映射文件示例：
  ```json
  { "f_15a": "F-15A 鹰", "cn_vt_5": "VT-5 轻坦" }
  ```

**几百 GB 资源目录的性能（懒加载）**：
- 启动即展示**上次运行时缓存的索引快照**，界面立即可用。
- 启动后在**后台线程**逐步对比实际文件（存在性/修改时间/状态），更新失效标记与状态变动，不阻塞 UI。

## 6. 数据组织（内部数据模型）

> 本节沉淀自"内部数据组织"讨论，描述**程序内存中的逻辑数据模型**与聚合关系。
> **物理落盘方式**（资源存储目录内文件如何组织）暂未定，见 §5。

### 6.1 实体总览

```
Country (国家, 配置目录)
 └─ Vehicle (载具)
      ├─ SkinPackages: List<SkinPackage>   // 该载具下所有涂装包
      └─ Parts: List<VehiclePart>          // 由所有包的 from 聚合

SkinPackage (涂装包, 资源存储目录)
 └─ Mappings: List<TexMapping>             // 该包 blk 内每条映射

Import (导入记录, 资源存储目录)             // 仅溯源标签, 非一等实体
```

### 6.2 各实体字段

**Import（仅溯源标签，最轻模型）**
- `Id`、`SourceType`（文件夹 / 压缩包 / 现有 UserSkins）、`SourcePath`、`ImportedAt`。
- 解构时给每个 SkinPackage 打上 `SourceImportId` 溯源；**删除包时不按批次回滚**，Import 不维护反向引用、不参与删除逻辑。

**Country（国家）**
- `Id`（如 `cn`、`us`、`unclassified`）、`Name`。
- 仅作 Vehicle 的标签；一个载具只属一个国家（移动载具 = 改其 CountryId），改动不影响文件物理位置。

**Vehicle（载具）**
- `Id`：内部标识 = blk 文件名（去扩展名），如 `f_15a`；用户可自定义改名（经映射文件）。
- `DisplayName`：显示名，来自映射文件；未映射时回退到 Id。
- `CountryId`：所属国家；前缀自动判定，无前缀 = `unclassified`，用户可改。
- `SkinPackages`：该载具下所有涂装包。
- `Parts`：由所有包的 `from` **去 `*` 归一化后聚合去重**得到的部件集合。
- **激活的涂装包**：见 `VehicleActivation`（§6.3）——每个载具同时只激活一套包，存于配置目录。

**VehiclePart（部件，从 from 聚合）**
- `From`：归一化部件位置键（去 `*` 后的唯一值）。
- `DisplayName`：暂 = `From` 原值，**不做部位翻译**（呼应格式文档 §6 命名不统一）。
- `Candidates`：各涂装包里 `from` 命中本部件的 `TexMapping` 列表（即同位置可选贴图来源）。
- 关键：**相同 `from` 字段 = 同一部件位置**，是匹配/替换的唯一依据。

**SkinPackage（涂装包）**
- `Id`：程序内稳定标识（如 GUID）。
- `SourceImportId`：溯源（见 Import）。
- `VehicleId`：所属载具。
- `Name`：用户自定义名，默认 = 源 blk 文件名。
- `PreviewPath`：png 预览图（可选）。
- **`Parts`：该包的部件贴图配置**（`from` → `to` + `mode`/`param`）——"用什么贴图"是**包自身的属性**。
  未配置过（`partsConfigured=false`）时沿用导入的 `source.blk`；属性界面保存后写入完整快照。
- `Mappings`：展开后的映射集合（`replace_tex` / `set_tex`），由 `Parts` 或 `source.blk` 解析得到；用于部件聚合与输出。

**TexMapping（贴图映射，Mode 跟着贴图走）**
- `From`：原模块代码（含/不含 `*` 均保留原值；部件聚合时去 `*` 比较）。
- `Mode`：`Replace` / `Set`，**默认从导入的 blk 读取**；用户在涂装包属性界面用**滑块**覆盖（滑块初值跟随所选贴图，改动结果写入该部件的 `parts` 条目，见 §3.6）。
- `Param?`：仅 `Set` 有（`camo_skin_tex`）。
- `To`：本包贴图文件名，如 `a.dds`。
- `TextureRef`：指向 `blobs/<hash>` 的**内容寻址引用**（去重核心）；输出到 WTSM 时按 `To` 名重命名后复制/硬链接。
- 注意：Mode 是**贴图属性**，不是部件属性；同一部件位置的不同候选贴图可能各自带不同 Mode。

### 6.3 激活与输出（VehicleActivation / ActiveLoadout）

- **载具激活** `VehicleActivation`：`{ activePackageId }`，存于**配置目录** `loadouts/<载具Id>.json`。
  每个载具同一时刻**只激活一套涂装包**；空 = 未激活（该载具无输出）。
- **部件贴图的选择属于包**（§3.6，存于该包 `meta.json` 的 `parts`），**不在这里逐部件选择**。
- **派生输出组合**：同步时由激活包派生 `ActiveLoadout` = `Dict<Part.From, SelectedMapping>`：
  - 键 = 部件位置（`from` 去 `*` 归一化后）
  - 值 = `SelectedMapping = { PackageId, TexMapping }`
- **输出 blk 时**：遍历派生出的每个部件，写出一条 `replace_tex` / `set_tex`：
  - `from` = 该包的 `from`（按需补回 `*`）
  - `Mode` = 该贴图的 `Mode`
  - `to` = 该包使用的贴图名，并把对应 dds 调度到 `<UserSkins>/WTSM/<载具Id>/`
- 因只改内容/贴图、不改 blk 文件名与路径 → 游戏热重载（§2.3）。

### 6.4 关键规则小结
- 部件由 `from` 聚合、去 `*` 归一化；相同 `from` = 同位置。
- **"用什么贴图"是涂装包自身的属性**（`meta.parts`，可在包属性界面配置/派生新组合）。
- **载具只记录"激活了哪一套包"**（`loadouts/<载具Id>.json`）；输出时由该包派生 blk 条目。
- `Mode` 随贴图走；载具显示名即 `from` 原值、不翻译。
- Import 仅溯源、不参与删除/回滚。

### 6.5 物理落盘（资源存储目录）
采用**逻辑/物理分离 + 内容寻址（去重）**：贴图按内容哈希存储为 blob，包只存 "`to` 名 → blob" 引用；文件物理位置与 国家/载具 逻辑层级解耦，国家改名、载具移动不搬文件。

```
<资源存储目录>/                     // 皮肤库（用户手动指定，可能几百G）
├── blobs/                         // 贴图内容寻址存储（去重核心）
│    └── <sha256>.<ext>            // 如 <sha256>.dds；相同内容只存一份
└── packages/<PackageId>/          // 包稳定标识(GUID)；与 国家/载具 完全解耦
     ├── source.blk                // 导入时原始 blk（保留溯源、程序不重写）
     └── meta.json                 // { vehicleId, name, sourceImportId, preview, order,
                                    //   partsConfigured, parts: [ { from, mode, to, param } ],
                                    //   textures: [ { to:"a.dds", blob:"<sha256>" } ] }
```

- **`parts` = 该包的部件贴图配置**（在涂装包属性界面保存后写入；`partsConfigured=false` 时沿用 `source.blk`）。
  改配置**只动 `meta.json`**，不重写 `source.blk` → 「导出原始模组」（§3.11）永远是导入时的原样。
- **国家/载具仅作为配置目录索引里的标签**，物理目录不体现 → 改名/移动零成本。
- **复制涂装包 = 零字节增量**：复制包只新建 `packages/<newId>/meta.json`（textures 映射指向相同 blob），不复制任何 dds；仅当用户替换某部件（指向别的 blob）或新增贴图时才产生新 blob。→ 解决"同包复制多份膨胀"问题。
- **跨包天然去重**：不同包引用相同内容的贴图，物理上只占一份 blob；删除包只删其 meta 引用，blob 在无引用后可**异步 GC**（可选）。
- **激活输出**生成在 `<UserSkins>/WTSM/<载具Id>/`（§2.2）；调度贴图时按 `ActiveLoadout` 的 `To` 名，把对应 blob **复制/硬链接**（同盘硬链接省空间，跨卷复制）到 WTSM 并重命名。
- **imports 溯源**（可选）：`imports/import_<id>.json` 记录每次导入来源，仅溯源用。
- 备注：导入时计算 hash 有 I/O 开销，在后台线程/缓存索引中完成，不阻塞 UI。
