# 线程池与长任务约定

> 适用范围：本仓库所有"可能持续数百毫秒以上"的后台工作 —— 解构 / 全量重建 / blob 回收 / 目录迁移 /
> 资源更新 / 数据清除 / 批量扫描 / 下载与校验。
>
> 本文是**唯一口径**：代码注释与本文件冲突时以本文件为准（并把注释顺手改回来）。

## 1. 一句话规则

**长任务不许长期占用线程池线程；并行的长任务必须用自己的线程。**

## 2. 为什么（.NET 线程池的实际行为）

- 每进程一个线程池；**默认最小线程数 = 处理器数**（`ThreadPool.GetMinThreads`）。
- 线程数**低于最小值时按需创建、比较积极**；一旦达到最小值，就交给"线程创建 / 销毁"算法
  （为**吞吐量**优化，俗称 hill-climbing）管理，**之后的新增被刻意限流**
  （社区常引用"约 500ms 一个"；这是实现细节，API 文档从未承诺）。
- 池有**最大线程数**上限（`GetMaxThreads`），满员后新工作项只能排队。
- 官方《The managed thread pool》把"**有会长时间阻塞线程的任务**"直接列入
  "**应该自己创建和管理线程**"的场景 —— 理由是池线程被大量阻塞会让别的任务起不来。

所以"后台在干活时界面卡顿"的成因**不是"池不会扩容"**，而是
**池的调节目标是吞吐量、不是响应性**：一批长期占用池线程的活，会让瀑布流缩略图的解码与
预览图取字节（同样走 `Task.Run`）排队等池按它的算法慢慢注入新线程。

## 3. 约定（可执行条款）

1. **并行**的长任务 → `DedicatedWorkers.Run(...)`
   （`Services/Infrastructure/DedicatedWorkers.cs`：专用 `Thread`，完全不用池）。
2. **顺序**的长任务 → 放进 `Task.Run` 即可（占 1 根池线程，可接受，这是全仓库的既定做法）。
   **不允许**在这里"顺手"再开并行 —— 那是第 1 条的活。
3. 并行度**必须**有上限（如 `ImportService.MaxDegree = 8`），并与"用户此刻是否在交互"挂钩：
   **与浏览并存的路径**（WT Live 静默导入）再减半（`SkinsViewModel.SilentImportDegree` = 核数一半，夹在 2..4）。
   理由已不是"抢线程池"，而是**抢 CPU 与磁盘带宽**（解构是 CPU + IO 双密集）。
4. **不要**把 `TaskCreationOptions.LongRunning` 当"专用线程"的契约：官方只承诺它是给调度器的一条
   **提示**（"oversubscription may be warranted"），"专用线程"是 `ThreadPoolTaskScheduler` 的
   实现细节。这条路径的存在意义就是"别用池线程"，所以就用 `Thread` 把它写成事实。
5. **不要**用 `ConcurrentExclusiveSchedulerPair` 之类"限流调度器"来"搬出池"：它们只限制并发数，
   任务**仍然执行在线程池上** —— 用来解决本文件的问题等于白用。
6. **不要**用 `ThreadPool.SetMinThreads` 治这个病：官方定位是"**临时绕过（temporarily work around）**"，
   并明确警告：可能过度订阅（被调度的线程在长队列里等时间片 → 反而延迟部分工作项）、
   work-stealing 扫描开销变大、上下文切换与 GC 线程栈遍历变多、进程内存上升，
   结论是"**大多数情况下线程池自己的分配算法表现更好**"。
   真要用，必须**先有诊断数据**（`ThreadPool.PendingWorkItemCount` / `ThreadCount`），且只当临时手段。
7. **禁止**在 UI 线程或池线程上 `.Result` / `.Wait()` / `GetAwaiter().GetResult()` 等长任务
   （本仓库当前没有，见「已知问题」里的 UI 线程审查记录；`ContinueWith` 回调里对**已完成**任务取
   `.Result` 不算）。
8. 阻塞型文件 IO 优先**真异步**（等磁盘时不占线程）—— **待评估**，见 §6。

## 4. 专用线程执行器（`DedicatedWorkers.Run`）

- 线程数 = `Clamp(degree, 1, 活的总数)`；活一次性入队（`ConcurrentQueue`），
  **每个元素恰好被交给一个 worker 一次**，处理顺序不保证。
- 线程是 `IsBackground = true`（进程退出不必等它）且命名为 `WTSM-longtask-N`
  （转储 / 调试器里一眼认出）。
- **取消在"活与活之间"生效**（与原 `Parallel.ForEach` 同一语义）：已取走的活会跑完；
  结束时若令牌已取消，**如实抛 `OperationCanceledException`**（哪怕活都做完了），
  调用方据此把结果标成"已取消"。
- **异常**：worker 里逃逸的异常会**终止整个进程**（与池线程同一后果），所以 worker 一律就地接住，
  记下第一个异常并让兄弟 worker 尽快停；等所有线程 `Join` 之后由**调用方线程**重抛，保留原始堆栈。

## 6. 已知边界与后续（如实记录，别当成"已解决"）

- **并发导入的线程数**：每路静默导入各拿 `SilentImportDegree` 根专用线程，N 路并发就是 N × degree 根。
  当前**没有全局闸门** —— 量级小（用户通常一两路）且每根只占 1 MB 栈；若将来出现多路并发导入，
  再考虑加一道"全局 worker 上限"。
- **调用方线程仍会 `Join`**：`DedicatedWorkers.Run` 是同步 API，调用方在收尾期间被挡住 ——
  那是**一根**线程，且调用点都经由 `Task.Run`（后台等待），与"8 根池线程被长期占住、
  害得别的活排队"不是一回事。若将来这条等待也要紧，再改成 `TaskCompletionSource` + `await`。
- **阻塞 IO 未异步化**：解构 / 复制仍用同步文件 IO + 哈希。哈希本身是 CPU（仍要占线程，但只占
  "真正在算"的时间），把"等磁盘"的那段也变成不占线程收益最大、改动也最大，单独立项，
  不顺手做。
- **`SetMinThreads` 未采用**（理由见 §3.6）。

## 7. 怎么自查

- 自检里有两条断言，掉了就说明约定被破坏：
  - `长任务线程`：专用线程数 ≤ 并行度、**来自线程池 = 0**、元素恰好处理一次、并发峰值 ≤ 并行度、
    已取消则一件不做、worker 里的异常由调用方线程重抛（既不吞、也不结束进程）；
  - `静默导入扰动`：并行度上限落在 2..4 且 ≤ 核数、`ResolveDegree` 的口径（0→按核数 / 显式值原样 /
    越界夹到 8 / 负数当默认）。
- 运行期观察：`ThreadPool.PendingWorkItemCount` / `ThreadPool.ThreadCount`（诊断计数），
  以及转储里的 `WTSM-longtask-*` 线程名。
