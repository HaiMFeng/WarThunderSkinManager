## 分级与书写规则

### 严重程度（Severity）

按**影响面**与**可绕过性**定级，等级号沿用业界通行的 Severity 四级（S1–S4）：

| 等级 | 名称 | 判定标准 |
| :--: | --- | --- |
| **S1** | 致命 Critical | 核心功能不可用、用户数据损坏或丢失、崩溃且无法绕过 |
| **S2** | 严重 High | 主要功能受损，或结果错误且没有合理的绕过手段 |
| **S3** | 一般 Medium | 次要功能异常或体验明显受损，存在可接受的绕过手段 |
| **S4** | 轻微 Low | 不影响功能：文案、性能、界面细节、代码结构等长期欠账 |

两条纪律：

- 严重程度描述问题**有多严重**，不等于修复先后。判不准时取**更低**等级，不夸大。
- 只用这四档，不新增加中间档（如 S2.5）；确有需要时用文字补充说明，保持等级之间可比。

### 书写格式

每条问题一个三级标题，标题为「编号 + 一句话结论」，字段固定、顺序固定：

```markdown
### KI-001 一句话说明问题与影响

- **严重程度**：S3（一般）
- **状态**：未修复 / 处理中
- **表现**：现象、触发条件、影响面
- **绕过**：用户可用的临时手段，没有就写「无」
- **思路**：计划怎么改；尚未想清时写「待评估」
```

编号 = `KI-` + 三位递增序号，一经分配不再复用，也不因排序调整而改号。

### 排列与归类

**不按「功能缺陷 / 代码结构 / 体验」等类别分节**：所有问题排在同一个清单里，按严重程度从高到低排列（同级按编号先后）。避免同一问题被归错类别、或在多处重复维护。

## 问题清单

### KI-001 多个源文件体积过大

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：7 个文件超过 500 行，其中 3 个接近 1900 行——`ViewModels/SkinsViewModel.cs`（1895）、`ViewModels/MainViewModel.cs`（1893）、`Dev/SelfTest.cs`（1887）；其余为 `ViewModels/PackageEditorViewModel.cs`（664）、`Services/Online/AppUpdateService.cs`（616）、`Services/Packages/ImportService.cs`（533）、`ViewModels/VehiclesViewModel.cs`（522）。阅读与定位成本高，改动时 diff 噪音大、易冲突。
- **绕过**：无（不影响功能）
- **思路**：按「行为不变的小步重构」推进——先确认自检覆盖了要动的代码路径，再按职责（加载 / 筛选 / 排序 / 命令等）抽成 `partial` 分部或协作类，每步跑构建与自检，保持 0 error / 0 warning、自检异常 0。注意：`Dev/SelfTest.cs` 的体量可能是刻意集中的（自检清单需要一览无余），拆它之前先确认发布自检脚本对它的约定。

### KI-002 瀑布流卡片累积到上千后的布局与位图开销（已做「窗口裁剪」，列宽变化仍全量重测）

- **严重程度**：S4（轻微）
- **状态**：部分修复
- **表现**：WT Live 浏览页（`Views/WtLiveView.xaml`）的瀑布流走非虚拟化的 `Controls/MasonryPanel`；列表只在新搜索时清空，滚动到底加载下一页会**持续累积**卡片。开发期规模探针（`Dev/MasonrySelfTest.MeasureThroughput`，固定随机种子、每张卡约 8 个元素）实测一次**完整冷布局**（测量 + 排列、所有子项都是脏的）：500 张 ≈ 170~250 ms、1500 张 ≈ 520~750 ms、3000 张 ≈ 1200~2400 ms（内容高 27496 / 82164 / 164445 px；绝对值随机器与负载波动，看斜率 ≈ **0.4~0.8 ms/张**、近似线性，**没有**退化到 O(N²)；护栏是「3000 张 > 3000 ms 才算异常」）。真正会咬人的是列宽变化（改窗口尺寸）：所有卡片的图片高度都绑在面板的 `ColumnWidth` 上，一变就整棵树失效 → 全量重测，卡片越多这次卡顿越明显。
- **已做（多面）**：
  1. **窗口裁剪**（`MasonryPanel.SetRealizedRange` / `GetRange`）：视图按滚动位置用面板缓存的**排布矩形**算出「保留实体」范围，窗口外的卡片**收起**（`Visibility.Collapsed`）——不再参与测量 / 渲染 / 命中测试；位置与高度取自缓存，**布局与滚动范围一字不变**（`MasonrySelfTest.CheckWindowTrim` 逐条钉住：总高、每块位置、命中范围；列宽变化会唤醒重排，且结果与「从零排一遍」完全一致）。同规模复测：3000 张里只留 50 张实体后**再布局一次 0.5 ms**（同规模全量 1400+ ms）。
  2. **高度缓存 + 数组复用**：`MeasureOverride` / `ArrangeOverride` 不再每次分配（列分配 / 高度 / 矩形三个平行数组全程复用），高度按「哪次列宽量的」作废并记归属（清空重开不会张冠李戴）。
  3. **缩略图随窗口释放**（`WtLiveViewModel.SetVisibleWindow` / `ReleaseThumbnail`）：窗口（3 屏）外的卡片**释放已解码位图并掐断在途下载**，滚回来按需从磁盘缓存重取（零网络）；并闸住「刚拉到的下一页整批取图」。此前卡片取过图就永不释放，滚过几千张后位图内存线性堆到几百 MB（每张 ≈ 解码宽 × 高 × 4 字节）。
- **仍在**：① **列宽变化（改窗口尺寸 / 拖到另一块屏）必然全量重测**——卡片高度依赖列宽，收起状态下量不出高度，只能先唤醒再量；② **首次布局**仍是 0.4~0.8 ms/张（分页 25 张/次 ≈ 20 ms，可感知但不明显）；③ 窗口裁剪省的是「测量 / 渲染 / 命中测试」，**视觉树本身仍在内存里**（3000 张 ≈ 10 万级视觉对象），只有真正的 UI 虚拟化（回收容器）才动得了这一项。
- **思路（后续）**：① 列宽变化：卡片高 = `列宽 / 宽高比` + 标题副标题固定高（`Controls/AspectRatioHeightConverter` 已用同一公式占位），可用估算高度表**先排位、再按需校正**，避免整棵树失效——代价是滚动条 / 锚点要对齐，风险高，收益有限时别动；② 视觉树：改成 `VirtualizingPanel` 系（接 `ItemContainerGenerator` 回收容器）或在现有 `Panel` 里按视口维护子项集合（后者与「滚动到底加载下一页」耦合更小）；③ 分帧构建：一页 25 张的模板实例化约 20 ms，可拆到几帧里增量插入。硬约束不变：布局算法（最短列优先、列宽发布给卡片绑定）与落位结果必须完全不变，`MasonrySelfTest` 的落位断言、窗口裁剪断言与规模探针都要继续通过。
