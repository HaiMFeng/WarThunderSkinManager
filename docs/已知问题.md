# 已知问题

记录已确认但尚未修复的问题。已修复的问题随版本发布说明归档，不在此保留。

## 分级与书写规则

### 严重程度（Severity）

按**影响面**与**可绕过性**定级，等级号沿用业界通行的 Severity 四级（S1–S4）：

| 等级 | 名称 | 判定标准 |
| :--: | --- | --- |
| **S1** | 致命 Critical | 核心功能不可用、用户数据损坏或丢失、崩溃且无法绕过 |
| **S2** | 严重 High | 主要功能受损，或结果错误且没有合理的绕过手段 |
| **S3** | 一般 Medium | 次要功能异常或体验明显受损，存在可接受的绕过手段 |
| **S4** | 轻微 Low | 不影响功能：文案、性能、界面细节、代码结构等长期欠账 |

两条纪律：

- 严重程度描述问题**有多严重**，不等于修复先后。判不准时取**更低**等级，不夸大。
- 只用这四档，不新增加中间档（如 S2.5）；确有需要时用文字补充说明，保持等级之间可比。

### 书写格式

每条问题一个三级标题，标题为「编号 + 一句话结论」，字段固定、顺序固定：

```markdown
### KI-001 一句话说明问题与影响

- **严重程度**：S3（一般）
- **状态**：未修复 / 处理中
- **表现**：现象、触发条件、影响面
- **绕过**：用户可用的临时手段，没有就写「无」
- **思路**：计划怎么改；尚未想清时写「待评估」
```

编号 = `KI-` + 三位递增序号，一经分配不再复用，也不因排序调整而改号。

### 排列与归类

**不按「功能缺陷 / 代码结构 / 体验」等类别分节**：所有问题排在同一个清单里，按严重程度从高到低排列（同级按编号先后）。避免同一问题被归错类别、或在多处重复维护。

## 问题清单

### KI-003 存在读不出元数据的包目录时，blob 回收整体放弃且界面没有任何提示

- **严重程度**：S3（一般）
- **状态**：未修复
- **表现**：blob 回收（`Services/Storage/BlobGc.cs`）先单遍扫描所有包的 `meta.textures` 收集引用集合；只要**有一个包目录的 `meta.json` 读不出**（建到一半的空目录 / 非原子写坏的文件），引用集合就不完整，于是**整体放弃本次回收**（安全设计，避免误删）。问题是这个放弃只写进 `report.Errors`，而后台入口的完成回调没有任何界面订阅 → 用户完全无感。叠加「删包会触发回收」这条路径，后果是**未被引用的贴图永久堆积、磁盘只增不减**，并且每次触发回收都白扫一遍全部包的 meta。
- **绕过**：手动清掉 `packages/` 下那些没有 `meta.json`（或 meta 损坏）的目录，回收即可恢复正常。
- **思路**：① 回收入口在 `Errors` 非空时写一次状态栏提示（告知"因 N 个包读不出，本次未清理缓存"），把静默变成可见；② `PackageStore.LoadAll` 对损坏 meta 的目录做一次显式登记（而不是静默跳过），使"哪些目录是坏的"成为一个可展示、可清理的清单。

### KI-004 激活输出可能删掉某张贴图在输出目录里的唯一副本

- **严重程度**：S3（一般）
- **状态**：未修复
- **表现**：激活输出（`Services/Packages/OutputService.cs`）里，映射的 `TextureRef` 有值但对应 blob 文件不存在时（仓储侧 blob 已被回收 / 被手工删掉），代码只记一条告警、**不加入待调度集合**；而随后的"清理不再被引用的贴图"以该集合为保留集，于是输出目录里那个同名旧文件会被删掉，紧接着写出的 blk **仍然引用这个 `to`**。净效果：原本还能正常显示（输出目录里那份可能是硬链接来的唯一副本）的贴图，被这次激活变成"贴图缺失"。前置条件是仓储 blob 已缺，所以不是常态，但一旦发生就是**把可用的输出改坏**。
- **绕过**：用「全量重建资源库」让 blob 引用重新落定；或把 `UserSkins/WTSM` 下该载具目录整个删掉重新激活。
- **思路**：清理前先判断"这个 `to` 是不是本次 blk 仍然引用的名字"，若输出目录里已有一份且本次只是因为缺 blob 而没调度，就**保留不删**（宁可留一个可能过期的文件，也不要把唯一副本删掉）；`to` 的语义是"游戏按图名加载"，留旧文件至少还能显示。

### KI-005 blk 一律按 UTF-8 读写，非 UTF-8 内容会破坏"未改动即逐字节相同"的承诺

- **严重程度**：S3（一般）
- **状态**：未修复
- **表现**：`BlkAssembler` 的文档承诺"未改动时输出与 `source.blk` 逐字节相同"，但读取（`BlkAssembler` / `DeconstructionService` / `ImportService`）统一用 `File.ReadAllText(path, Encoding.UTF8)`，写出也是 UTF-8 无 BOM。对 UTF-8 / ASCII 的 blk 完全成立；对 **GBK 等编码写的 blk**（作者机器环境不同），字节会被解成替换字符后再以 UTF-8 写出，往返不再逐字节相同；**带 BOM 的 blk** 输出会丢 BOM。战雷 blk 基本是 ASCII，所以实践影响小，但这是"往返一致性"这条护栏上一个明确的漏洞。
- **绕过**：无（不影响功能；受影响的是往返比对的严格性）
- **思路**：不改编码判定的前提下，把"逐字节往返"改成"**按检测到的编码解出同一字符序列**"；或者读取时记录 BOM / 编码，写出时原样还原。至少在 `BlkAssembler` 的文档里把"逐字节相同"限定为"对 UTF-8 / ASCII 的 blk"。

### KI-007 配置读取失败会回退默认值并随后落盘，可能覆盖真实配置

- **严重程度**：S3（一般）
- **状态**：未修复（历史遗留）
- **表现**：`ConfigService.Load` 对任何读异常（文件被占用 / 解码失败）都**返回默认 `AppConfig`**（三个目录为空）；启动流程随后因「Saves 目录为空」触发一次自动落盘，于是默认值被写回 `config.json`——用户的资源 / UserSkins 目录设置与语言选择就此丢失。依赖一次瞬时读失败（杀软扫描、云同步占位），概率低，但一旦命中就是"设置被清空"。
- **绕过**：出现后重新在设置页选一次三个目录。
- **思路**：把"读失败"与"文件不存在"区分开——读失败时**标记为只读降级**并禁用自动落盘（界面提示配置未能读取），只有用户显式改设置才写回；或写入前先备份原文件（`config.json.bak`）。

### KI-049 退出清理「零等待 + 立刻删暂存」：与在途导入抢目录，且没有任何退出钩子兜底

- **状态**：未修复（**当前不可达** —— 该视图只做 `Visibility` 切换、不走 `Unloaded`；登记它是给"将来改成可卸载页面"留判据）
- **表现**：`UnhookHostResize`（`Views/WtLiveView.xaml.cs:193-200`）解绑窗口的 `ResizeStarted/ResizeEnded` 时只清 `_resizeHost`、**不清 `_panel`**；而 `HookColumnWidth`（`:130-139`）以 `_panel != null` 当作"已经挂过"的判据 → 卸载再加载后直接 return，`BeginResize/EndResize` 再也不被调用，拖动缩放的冻结优化**静默失效**（不报错，只是拖动变卡）。另外 `_panel.ColumnWidthChanged` / `panel.WindowChanged` / `window.DpiChanged` 三个 lambda（`:157`、`:163`、`:168`）从不退订，面板实例被替换时是实打实的引用泄漏。
- **绕过**：无（当前路径触发不到）
- **思路**：三个回调存成字段，在 `UnhookHostResize` 里一并 `-=` 并清掉 `_panel`；`HookColumnWidth` 改用独立的"是否已订阅"标志，不再拿 `_panel` 兼职。

### KI-056 检查更新撞上"更新进行中"闸门时静默无反馈

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：`CheckAppUpdateCoreAsync` 开头是 `if (IsMaintenance) return;`（`ViewModels/MainViewModel.cs:2264`）——下载 / 安装进行中点「检查更新」、或切换「安装源」触发的重查，会被直接忽略且**不留任何提示**，看起来像按钮失灵。另一半：45 秒启动期自动检查与手动检查共用同一入口，但 24 小时节流只写在 `InitAppUpdate` 里，Core 内没有 —— 用户在 45 秒内手动检查过，定时器到点仍会再查一次（多余请求，结果相同、无害）。
- **绕过**：等当前操作（下载 / 安装）结束后再点
- **思路**：早退时给一句 `settings.appUpdate.busy`（键已存在，文案就是"请等待当前操作完成"）；把 24h 节流下沉到 Core，让两条入口共用同一套判据。

### KI-057 载具图标：断网时逐行重试、换配置目录不清理在途任务

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：① 断网时每滚到一行就发一次请求（**失败不写负缓存是刻意的**，但没有降频 / 熔断），
  `MaxConcurrency = 6` 很快被离线行占满，连本该成功的图标也要排队；
  ② `VehicleIconService.Configure()` 只清 `Memory` / `NoIcon`，不清 `Inflight`、也不取消在途任务 ——
  运行中换配置目录时，在途任务会往新目录写盘，并把旧目录的结论（含 404）写进内存缓存，需重启才恢复。
- **绕过**：重启程序；或等网络恢复
- **思路**：失败按 id 记 `RetryAfter`（30–120 秒），连续失败 N 次再来一个 60 秒全局熔断；
  `Configure` 换目录时递增 epoch，`LoadAsync` 回填前比对 epoch，不一致就丢弃。

### KI-058 下载条：进度回调没有轮次号，重试后旧回调可能穿过状态闸门

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：`Progress<T>` 的回调投递到 UI 队列，上一轮（被取消 / 失败）排队未执行的回调，
  在新一轮进入 `Importing` 后可以重新通过 `item.State != Importing` 判定，把进度抬到旧值；
  `Math.Max` 只保证不倒退，保证不了不超前。
- **绕过**：无（纯显示层小瑕疵，不影响实际下载 / 安装）
- **思路**：`WtLiveDownloadItem` 加 `internal int RunGeneration`，每轮入口 `++` 并保存局部值，
  三个回调统一 `gen != item.RunGeneration` 就丢弃。
