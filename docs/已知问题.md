## 分级与书写规则

### 严重程度（Severity）

按**影响面**与**可绕过性**定级，等级号沿用业界通行的 Severity 四级（S1–S4）：

| 等级 | 名称 | 判定标准 |
| :--: | --- | --- |
| **S1** | 致命 Critical | 核心功能不可用、用户数据损坏或丢失、崩溃且无法绕过 |
| **S2** | 严重 High | 主要功能受损，或结果错误且没有合理的绕过手段 |
| **S3** | 一般 Medium | 次要功能异常或体验明显受损，存在可接受的绕过手段 |
| **S4** | 轻微 Low | 不影响功能：文案、性能、界面细节、代码结构等长期欠账 |

两条纪律：

- 严重程度描述问题**有多严重**，不等于修复先后。判不准时取**更低**等级，不夸大。
- 只用这四档，不新增加中间档（如 S2.5）；确有需要时用文字补充说明，保持等级之间可比。

### 书写格式

每条问题一个三级标题，标题为「编号 + 一句话结论」，字段固定、顺序固定：

```markdown
### KI-001 一句话说明问题与影响

- **严重程度**：S3（一般）
- **状态**：未修复 / 处理中
- **表现**：现象、触发条件、影响面
- **绕过**：用户可用的临时手段，没有就写「无」
- **思路**：计划怎么改；尚未想清时写「待评估」
```

编号 = `KI-` + 三位递增序号，一经分配不再复用，也不因排序调整而改号。

### 排列与归类

**不按「功能缺陷 / 代码结构 / 体验」等类别分节**：所有问题排在同一个清单里，按严重程度从高到低排列（同级按编号先后）。避免同一问题被归错类别、或在多处重复维护。

## 问题清单

### KI-001 多个源文件体积过大

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：7 个文件超过 500 行，其中 3 个接近 1900 行——`ViewModels/SkinsViewModel.cs`（1895）、`ViewModels/MainViewModel.cs`（1893）、`Dev/SelfTest.cs`（1887）；其余为 `ViewModels/PackageEditorViewModel.cs`（664）、`Services/Online/AppUpdateService.cs`（616）、`Services/Packages/ImportService.cs`（533）、`ViewModels/VehiclesViewModel.cs`（522）。阅读与定位成本高，改动时 diff 噪音大、易冲突。
- **绕过**：无（不影响功能）
- **思路**：按「行为不变的小步重构」推进——先确认自检覆盖了要动的代码路径，再按职责（加载 / 筛选 / 排序 / 命令等）抽成 `partial` 分部或协作类，每步跑构建与自检，保持 0 error / 0 warning、自检异常 0。注意：`Dev/SelfTest.cs` 的体量可能是刻意集中的（自检清单需要一览无余），拆它之前先确认发布自检脚本对它的约定。

### KI-002 瀑布流卡片累积到上千后，一次全量布局约 0.4 ms/张

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：WT Live 浏览页（`Views/WtLiveView.xaml`）的瀑布流走非虚拟化的 `Controls/MasonryPanel`，`MeasureOverride` 会对**每个**子项调一次 `child.Measure`；列表只在新搜索时清空，滚动到底加载下一页会**持续累积**卡片。开发期规模探针（`Dev/MasonrySelfTest.MeasureThroughput`，固定随机种子、每张卡约 8 个元素）实测一次**完整冷布局**（测量 + 排列、所有子项都是脏的）：500 张 = 249 ms、1500 张 = 746 ms、3000 张 = 1232 ms（内容高 27496 / 82164 / 164445 px；绝对值随机器波动，看斜率）。结论：约 **0.4 ms/张**、近似线性，**没有**退化到 O(N²)——自检护栏是「3000 张 > 3000 ms 才算异常」，当前离护栏尚有余量。真正会咬人的是列宽变化（窗口尺寸改变）：所有卡片的图片高度都绑在面板的 `ColumnWidth` 上，一变就整棵树失效 → 全量重测，卡片越多这次卡顿越明显。
- **绕过**：无（当前分页量级下基本感知不到；新搜索会清空列表）
- **思路**：瀑布流的高度**本来就可以不算**——卡片高 = `列宽 / 宽高比` + 标题副标题固定高，`Controls/AspectRatioHeightConverter` 已经用同一公式给缩略图占位。所以：(1) 纯算术先排出「落位表」（最短列优先，不算 measure）；(2) 只实体化并测量**视口 ±1 屏**内的子项，其余用同高的轻量占位块顶住高度，避免占位块自己变成新成本。落地形态二选一：改成 `VirtualizingPanel` 系（接 `ItemContainerGenerator`），或在现有 `Panel` 里按视口自己维护子项集合——后者与「滚动到底加载下一页」耦合更小。硬约束：布局算法（最短列优先、列宽发布给卡片绑定）与落位结果必须完全不变，`MasonrySelfTest` 的落位断言与规模探针都要继续通过；建议顺手给探针补一条「估算高度表 == 实际测量高度」的断言，否则估算公式会随卡片模板悄悄漂移（标题换行、副标题缺失都会影响固定高那部分）。
