# 已知问题

记录已确认但尚未修复的问题。已修复的问题随版本发布说明归档，不在此保留。

## 分级与书写规则

### 严重程度（Severity）

按**影响面**与**可绕过性**定级，等级号沿用业界通行的 Severity 四级（S1–S4）：

| 等级 | 名称 | 判定标准 |
| :--: | --- | --- |
| **S1** | 致命 Critical | 核心功能不可用、用户数据损坏或丢失、崩溃且无法绕过 |
| **S2** | 严重 High | 主要功能受损，或结果错误且没有合理的绕过手段 |
| **S3** | 一般 Medium | 次要功能异常或体验明显受损，存在可接受的绕过手段 |
| **S4** | 轻微 Low | 不影响功能：文案、性能、界面细节、代码结构等长期欠账 |

两条纪律：

- 严重程度描述问题**有多严重**，不等于修复先后。判不准时取**更低**等级，不夸大。
- 只用这四档，不新增加中间档（如 S2.5）；确有需要时用文字补充说明，保持等级之间可比。

### 书写格式

每条问题一个三级标题，标题为「编号 + 一句话结论」，字段固定、顺序固定：

```markdown
### KI-001 一句话说明问题与影响

- **严重程度**：S3（一般）
- **状态**：未修复 / 处理中
- **表现**：现象、触发条件、影响面
- **绕过**：用户可用的临时手段，没有就写「无」
- **思路**：计划怎么改；尚未想清时写「待评估」
```

编号 = `KI-` + 三位递增序号，一经分配不再复用，也不因排序调整而改号。

### 排列与归类

**不按「功能缺陷 / 代码结构 / 体验」等类别分节**：所有问题排在同一个清单里，按严重程度从高到低排列（同级按编号先后）。避免同一问题被归错类别、或在多处重复维护。

## 问题清单

### KI-003 存在读不出元数据的包目录时，blob 回收整体放弃且界面没有任何提示

- **严重程度**：S3（一般）
- **状态**：未修复
- **表现**：blob 回收（`Services/Storage/BlobGc.cs`）先单遍扫描所有包的 `meta.textures` 收集引用集合；只要**有一个包目录的 `meta.json` 读不出**（建到一半的空目录 / 非原子写坏的文件），引用集合就不完整，于是**整体放弃本次回收**（安全设计，避免误删）。问题是这个放弃只写进 `report.Errors`，而后台入口的完成回调没有任何界面订阅 → 用户完全无感。叠加「删包会触发回收」这条路径，后果是**未被引用的贴图永久堆积、磁盘只增不减**，并且每次触发回收都白扫一遍全部包的 meta。
- **绕过**：手动清掉 `packages/` 下那些没有 `meta.json`（或 meta 损坏）的目录，回收即可恢复正常。
- **思路**：① 回收入口在 `Errors` 非空时写一次状态栏提示（告知"因 N 个包读不出，本次未清理缓存"），把静默变成可见；② `PackageStore.LoadAll` 对损坏 meta 的目录做一次显式登记（而不是静默跳过），使"哪些目录是坏的"成为一个可展示、可清理的清单。

### KI-004 激活输出可能删掉某张贴图在输出目录里的唯一副本

- **严重程度**：S3（一般）
- **状态**：未修复
- **表现**：激活输出（`Services/Packages/OutputService.cs`）里，映射的 `TextureRef` 有值但对应 blob 文件不存在时（仓储侧 blob 已被回收 / 被手工删掉），代码只记一条告警、**不加入待调度集合**；而随后的"清理不再被引用的贴图"以该集合为保留集，于是输出目录里那个同名旧文件会被删掉，紧接着写出的 blk **仍然引用这个 `to`**。净效果：原本还能正常显示（输出目录里那份可能是硬链接来的唯一副本）的贴图，被这次激活变成"贴图缺失"。前置条件是仓储 blob 已缺，所以不是常态，但一旦发生就是**把可用的输出改坏**。
- **绕过**：用「全量重建资源库」让 blob 引用重新落定；或把 `UserSkins/WTSM` 下该载具目录整个删掉重新激活。
- **思路**：清理前先判断"这个 `to` 是不是本次 blk 仍然引用的名字"，若输出目录里已有一份且本次只是因为缺 blob 而没调度，就**保留不删**（宁可留一个可能过期的文件，也不要把唯一副本删掉）；`to` 的语义是"游戏按图名加载"，留旧文件至少还能显示。

### KI-005 blk 一律按 UTF-8 读写，非 UTF-8 内容会破坏"未改动即逐字节相同"的承诺

- **严重程度**：S3（一般）
- **状态**：未修复
- **表现**：`BlkAssembler` 的文档承诺"未改动时输出与 `source.blk` 逐字节相同"，但读取（`BlkAssembler` / `DeconstructionService` / `ImportService`）统一用 `File.ReadAllText(path, Encoding.UTF8)`，写出也是 UTF-8 无 BOM。对 UTF-8 / ASCII 的 blk 完全成立；对 **GBK 等编码写的 blk**（作者机器环境不同），字节会被解成替换字符后再以 UTF-8 写出，往返不再逐字节相同；**带 BOM 的 blk** 输出会丢 BOM。战雷 blk 基本是 ASCII，所以实践影响小，但这是"往返一致性"这条护栏上一个明确的漏洞。
- **绕过**：无（不影响功能；受影响的是往返比对的严格性）
- **思路**：不改编码判定的前提下，把"逐字节往返"改成"**按检测到的编码解出同一字符序列**"；或者读取时记录 BOM / 编码，写出时原样还原。至少在 `BlkAssembler` 的文档里把"逐字节相同"限定为"对 UTF-8 / ASCII 的 blk"。

### KI-006 内容去重命中时不刷新 blob 时间戳，10 分钟宽限期保护在窄窗口下失效

- **严重程度**：S3（一般）
- **状态**：未修复
- **表现**：`BlobStore.Store` 在"同内容 blob 已存在"时只丢弃临时文件、**不触碰已有文件的时间戳**；而回收的宽限期保护（`BlobGc`）判据正是"文件最后写入时间早于 10 分钟 → 可删"。窄窗口竞态：删包触发回收（引用快照已取）→ 与此同时 / 其后导入的新包因内容去重复用了那个旧文件（mtime 很旧、且不在已取的引用集里）→ 回收的删除循环把它删掉 → 新包的 `meta.textures` 指向一个不存在的 blob → 该部件无贴图。回收在"程序忙"时不启动、删除与导入通常串行，所以可达性低。
- **绕过**：无（触发概率低）；出现后可重跑「全量重建资源库」重新落定引用。
- **思路**：去重命中即 `File.SetLastWriteTimeUtc(dest, now)`（"刚被使用"语义），或在回收内对"扫描开始之后被动过"的文件再做一次复核。代价是批量导入时去重命中会各多一次 mtime 写，需实测其对导入耗时的影响。

### KI-007 配置读取失败会回退默认值并随后落盘，可能覆盖真实配置

- **严重程度**：S3（一般）
- **状态**：未修复（历史遗留）
- **表现**：`ConfigService.Load` 对任何读异常（文件被占用 / 解码失败）都**返回默认 `AppConfig`**（三个目录为空）；启动流程随后因「Saves 目录为空」触发一次自动落盘，于是默认值被写回 `config.json`——用户的资源 / UserSkins 目录设置与语言选择就此丢失。依赖一次瞬时读失败（杀软扫描、云同步占位），概率低，但一旦命中就是"设置被清空"。
- **绕过**：出现后重新在设置页选一次三个目录。
- **思路**：把"读失败"与"文件不存在"区分开——读失败时**标记为只读降级**并禁用自动落盘（界面提示配置未能读取），只有用户显式改设置才写回；或写入前先备份原文件（`config.json.bak`）。

### KI-001 多个源文件体积过大

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：8 个文件超过 500 行——`Dev/SelfTest.cs`（2690，含本迭代新增的 WT Live / 瀑布流探针）、`ViewModels/MainViewModel.cs`（1761）、`ViewModels/SkinsViewModel.cs`（1624）、`Themes/ThemeResources.xaml`（1282）、`ViewModels/WtLiveViewModel.cs`（777）、`Views/WtLiveView.xaml`（653）、`ViewModels/PackageEditorViewModel.cs`（570）、`Views/SettingsView.xaml`（549）。阅读与定位成本高，改动时 diff 噪音大、易冲突。
- **绕过**：无（不影响功能）
- **思路**：按「行为不变的小步重构」推进——先确认自检覆盖了要动的代码路径，再按职责（加载 / 筛选 / 排序 / 命令等）抽成 `partial` 分部或协作类，每步跑构建与自检，保持 0 error / 0 warning、自检异常 0。注意：`Dev/SelfTest.cs` 的体量可能是刻意集中的（自检清单需要一览无余），拆它之前先确认发布自检脚本对它的约定。

### KI-002 瀑布流：列宽变化仍全量重测，首次布局仍是逐张线性

- **严重程度**：S4（轻微）
- **状态**：部分修复
- **表现**：WT Live 浏览页的瀑布流本迭代已换成**真虚拟化**面板（`Controls/VirtualizingMasonryPanel`：接 `ItemContainerGenerator` 回收容器、滚动范围按估算高度表给出），原「滚动每步成本随卡片总数线性增长」与「位图内存随滚动线性堆高」两条已消除（旧版是"非虚拟化面板 + 只收起窗口外卡片"）。**仍在**：① **列宽变化（改窗口尺寸 / 拖到另一块屏）必然全量重测**——卡片高度由列宽下推，收起状态下量不出高度，只能先唤醒再量，卡片越多这次卡顿越明显；② **首次布局**仍是每张 0.4~0.8 ms（分页 25 张/次 ≈ 20 ms，可感知但不明显）；③ 估算高度表在未测量的区域与实测值有偏差，滚动条长度与内容位置会有小幅漂移（虚拟化的固有取舍）。
- **绕过**：无（不影响功能）
- **思路**：① 列宽变化只在**拖拽结束**时重测（拖动中先用估算高度顶住，避免逐帧全量）；② 首次布局分帧构建（一页 25 张拆到几帧里增量插入）。硬约束不变：布局算法（最短列优先、列宽发布给卡片绑定）与落位结果必须完全不变，`MasonrySelfTest` 的落位断言与规模探针都要继续通过。

### KI-008 预览图缓存键在「浏览缩略图」与「下载」两条链路上不一致，跨链路永不命中

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：缓存键 = URL 的 SHA-256 前 32 位。浏览链路用**清晰度变体 URL**（经 `WtLiveQualityCatalog.ResolveUrl`，低清档即 `_lq`）读写缓存；下载链路用的却是帖子详情接口给的原图 URL（`images[].orig.src`，不带 `_lq`）。两条 URL 不同 → 缓存键不同，**除非用户先打开过详情浮窗**（详情第 0 张用的也是原图 URL），否则下载时那句"预览图优先吃缓存"永远不成立，只是多下一次图。属口径不一致，不是功能缺陷。
- **绕过**：无（仅多一次下载流量）
- **思路**：统一成"下载链路也走 `ResolveUrl(原图 URL, 当前清晰度)`"，或让两条链路共享一个"同一个帖子的预览图"规范化键（按帖子 id）。

### KI-009 批量导入时，同一载具多个新包的初始显示顺序不确定

- **严重程度**：S4（轻微）
- **状态**：未修复（历史遗留）
- **表现**：`Services/Packages/ImportService.cs` 用 `Parallel.ForEach` 解构，结果按各 worker 的**完成顺序**追加到集合，随后 `AssignOrder` 按这个顺序给同一载具的新包分配连续 `Order`。因此一次批量导入里同载具多个新包的初始显示顺序不确定（相对顺序不影响功能正确性，用户也可拖动排序）。
- **绕过**：导入后在涂装管理页手动排序。
- **思路**：`Order` 分配改成按"来源顺序 + 包在压缩包里的相对路径"稳定排序，而不是按完成顺序。

### KI-010 收藏浮窗拖拽排序时，每越过一格就整表原子落盘

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：拖拽排序的 `DragOver` 按 80 ms 节流，每次命中即调用 `Move(...)`，而 `Move` 内部立即 `Persist()` → **全量重写**收藏 JSON（原子写）。鼠标划过一整列时约 12 次/秒的整表落盘。数据量小（几十条），影响轻微，但属于"没必要那么频繁"的 IO。
- **绕过**：无（不影响功能）
- **思路**：拖拽过程中的 `Move` 只改内存顺序并置"脏"标记，`Drop`（或节流 1~2 s）时才落盘一次。

### KI-011 详情浮窗打开期间，窗口级键盘闸门会吞掉左右方向键

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：`MainWindow` 的隧道键处理在 `WtLive.Detail.IsOpen` 时无条件接管 `Left` / `Right`（用于切换浮窗里的上一张 / 下一张）。若用户此刻正聚焦在浮窗的正文只读文本框里，左右键就不能移动光标 / 扩选（上下键未被拦截，仍可用）。属有意的取舍，但对"想复制正文一段文字"的用户是干扰。
- **绕过**：用上下键或鼠标在正文里定位。
- **思路**：仅在"焦点不在文本输入类控件内"时才接管左右键（判 `Keyboard.FocusedElement is not TextBoxBase`）。

### KI-012 崩溃日志固定写到默认配置目录，与其余数据不同源

- **严重程度**：S4（轻微）
- **状态**：未修复（历史遗留）
- **表现**：`App.xaml.cs` 的全局异常兜底用 `ConfigService.DefaultConfigDirectory()` 拼日志路径，即使用户已经把配置目录改到别处，`crash-log.txt` 仍落在默认的 `%LOCALAPPDATA%` 下，与配置、语言文件、索引快照不在同一处。
- **绕过**：去默认位置找日志文件。
- **思路**：崩溃兜底是启动早期代码（配置可能还没读出来），可先尝试已读到的配置目录、失败再回落默认目录；并在日志首行写明实际路径。

### KI-013 blk 解构对「贴图缺失」不缓存负结果，同名的后续映射重复做系统调用

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：`Services/Packages/DeconstructionService.cs` 里，某个 `to` 解析不到贴图时直接 `continue`，没有把"这个 `to` 找不到"写进解析缓存，于是同一 `to` 在后续每条映射上都会再走一遍 `File.Exists` + 目录枚举。仅影响解构耗时（目录清单本身已有按写入时间的缓存，故开销有限）。
- **绕过**：无
- **思路**：把负结果（`null`）也写进 `storedTo` 缓存。

### KI-014 原子写留下的 `.tmp` 残留，对配置与元数据目录永不清理

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：`Services/Storage/AtomicFile.cs` 的 `.tmp` 落在**各自的目标目录**，而它的注释声称"`.tmp` 残留由 blob 回收一并清理（见 `BlobGc`）"——但 `BlobGc` 只枚举 `blobs/` 下的文件，`packages/*/meta.json.tmp`、`config.json.tmp`、`index/library.json.tmp` 等崩溃残留**永远不会被清理**。属文档断言与实现不符 + 微量磁盘残留。
- **绕过**：手动删除。
- **思路**：要么让 `BlobGc` 顺带清扫这些目录下的 `*.tmp`（超过宽限期的），要么把注释里的承诺改成"不清理，仅由用户手动处理"。

### KI-015 blob 回收按「去扩展名」匹配引用，同哈希的孤儿副本不回收

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：`BlobGc` 判断一个 blob 是否被引用时，拿 `Path.GetFileNameWithoutExtension(blob)`（纯哈希）去比对 `meta.textures[].Blob`（也是纯哈希）。因此**同一内容若存在两个扩展名的文件**（如 `abc.dds` 与 `abc.tga`），只要其中一个扩展名被引用，另一个（真孤儿）也会被判为"被引用"而**永不回收**。残留量小（同内容不同扩展名本身罕见）。
- **绕过**：手动删除。
- **思路**：引用比对改成"哈希 + 扩展名"精确匹配（`meta.textures` 里同时记了 `to` 的扩展名），或让回收把"哈希命中但扩展名不匹配"的文件单独计一份并提示。

### KI-016 导出侧存在未被调用的同名贴图去重方法（死代码）

- **严重程度**：S4（轻微）
- **状态**：未修复
- **表现**：`Services/Packages/OutputService.UniqueTextureName` 在仓库内没有任何调用点；同名 `to` 撞名的处理实际在导出侧（`PackageExporter.UniqueRelativeName`）另有实现。属代码卫生欠账，容易误导后来者以为激活输出也做了重名去重。
- **绕过**：无（不影响功能）
- **思路**：确认导出侧的实现确实覆盖了原意图后删掉该方法，或反之把它接上并删掉重复实现。
