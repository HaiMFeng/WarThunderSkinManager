# 更新体积与增量更新评估

> **本文是评估记录，不是设计规格，也不代表任何已实施改动。**
>
> - 结论：**暂不实施**（详见 §5）。当前的发布物形态（单文件 payload + Inno 安装器 + 应用内全量自更新）保持不变；
> - 本文不改变 `docs/应用自更新设计.md` 的任何决策（§11 不变量、§13「不做增量/差分更新」仍然有效）；
> - 若将来重启，需另立设计文档并走完整评审，**不要**直接把本文当实施清单。
>
> 评估时间：2026-10-26（基线 v0.3.4-dev）· 环境：SDK 10.0.300 / runtime 10.0.8 / win-x64
> 体积单位按 1 MB = 1024 KB 计。

## 1. 动机

每次发版，安装版用户都要重新下载完整的 59.7 MB 安装器，而两版之间真正变化的内容很少。
本文要回答三个问题：**60 MB 里都是什么、哪些会随版本变、值不值得做增量更新。**

## 2. 实测数据

### 2.1 产物是两层压缩

```
Setup 59.7 MB          ← Inno LZMA2（solid）把 payload 再压一遍
  └─ payload exe 64.6 MB   ← .NET 单文件包：402 个文件（未压缩合计 153.5 MB）逐个 deflate
       └─ 其中 395 个文件是 .NET / WPF 运行时
```

### 2.2 64.6 MB 的构成

| 组 | 文件数 | 未压缩 | 压缩后 | 占比 |
|---|---:|---:|---:|---:|
| .NET 托管运行时（`System.*` / `Microsoft.*` / `Presentation*`） | 384 | 119.7 MB | 52.5 MB | 80.5% |
| 原生运行时（`coreclr` `clrjit` `wpfgfx_cor3` `PresentationNative_cor3` `D3DCompiler_47` …） | 11 | 19.4 MB | 9.4 MB | 14.4% |
| 本项目程序集（含全部内嵌资源） | 2 | 11.5 MB | 1.84 MB | 2.8% |
| 第三方（`SharpCompress` / `CommunityToolkit.Mvvm`） | 2 | 2.5 MB | 1.12 MB | 1.7% |
| 其它（`deps.json` / `runtimeconfig.json` 等） | 3 | 0.5 MB | 0.33 MB | 0.5% |

压缩后最大的文件（MB）：`PresentationFramework` 6.92、`System.Private.CoreLib` 6.53、`PresentationCore` 3.49、
`System.Private.Xml` 3.38、`coreclr` 2.28、`D3DCompiler_47_cor3` 2.12、**`WarThunderSkinManager.dll` 1.75**、
`System.Data.Common` 1.26、`System.Linq.Expressions` 1.22、`clrjit` 1.11。
按技术栈切：WPF 桌面栈 22.6 MB（35%），其余 42.5 MB（65%）。

### 2.3 我们自己的部分只有 1.84 MB（2.8%）

`WarThunderSkinManager.dll` 未压缩 11.32 MB：

| 内容 | 未压缩 | 压缩后 |
|---|---:|---:|
| `units.csv`（载具译名，`EmbeddedResource`） | 5.69 MB | 0.59 MB |
| `units_weaponry.csv`（武器名） | 3.68 MB | 0.49 MB |
| `shop.blkx`（国家归属） | 0.36 MB | 0.04 MB |
| `fa-solid-900.otf`（Font Awesome） | 0.40 MB | 0.18 MB |
| `symbols_skyquake.ttf` / 语言表 / 图标 / logo | 0.18 MB | ≈0.07 MB |
| 业务代码本体 | ≈1.00 MB | ≈0.4 MB |

### 2.4 跨版本真正变化的字节

用 v0.3.3-dev 标签在临时 worktree 里重建 payload，与 v0.3.4-dev 比对：

| 比对方式 | 结果 |
|---|---|
| 4 KB **定长**块对齐 | 只有 14.8% 相同（插入位移会让定长块全错位，**不能**用这种方式估增量） |
| **内容定界**切块（CDC，平均 16 KB） | **62.80 / 64.58 MB 完全相同（97.3%），新增 1.77 MB，仅 10 段交替** |

两版公共前缀 7.96 MB。差异集中在"本项目程序集 + 包尾清单"。
→ 相邻两版的理论增量约 **2 MB**（含索引开销），但**升 .NET 运行时的那一版会退化到 ~50 MB**，
体积不可预测，无法写成固定判据。

### 2.5 哪些不变、哪些会变

| 部分 | 压缩后 | 变不变 | 依据 |
|---|---:|---|---|
| .NET 10.0.8 托管 + 原生运行时 | 61.8 MB（95.7%） | 只有升 SDK / 运行时才变 | 抽样 8 个文件（`System.Private.CoreLib` `coreclr` `clrjit` `PresentationFramework` `PresentationCore` `PresentationNative_cor3` `wpfgfx_cor3` `ReachFramework`）的 SHA256 与 `C:\Program Files\dotnet\shared\...\10.0.8` **逐一相同**；`runtimeconfig.json` 记的也是 10.0.8 |
| 第三方包 | 1.12 MB | 只有升 NuGet 才变 | `SharpCompress 0.50.4` / `CommunityToolkit.Mvvm 8.4.2` |
| 业务代码 + 内嵌资源 | 1.84 MB | **每版必变** | — |
| └ 三张数据表 | 1.12 MB | 每次发布例行更新 | v0.3.4-dev 三张全换（`units.csv` 445+/155−、`units_weaponry.csv` 857+/519−、`shop.blkx` 48+/47−） |
| └ 语言表 | 0.02 MB | 改文案就变 | `zh-CN.json` 历史 110 次提交 |
| └ 字体 / 图标 / logo | ≈0.25 MB | 极少变 | 字体 2026-10-07、图标 2026-09-25 |

## 3. 三条备选路线

### A. 单文件 payload + 二进制补丁

- **结构障碍**：`installer\WarThunderSkinManager.iss` 用 `Compression=lzma2/ultra64` + `SolidCompression=yes`，
  且 `[Files]` 只有一条（巨大的 payload）→ Setup 内部是**单块 LZMA**。payload 在 8 MB 处的改动会让其后的
  整个压缩流重编码，两个 Setup 的差分约 52 MB，等于全量。改成非 solid 也无用（只有一个文件）。
- 因此补丁只能打在 **payload** 上，而 payload 不是安装包 → 必须**绕开安装器**：直接替换
  `{app}\WarThunderSkinManager.exe`（安装目录里就那么一个文件）。
- 副作用：绕过 Inno 的原子性/回退；运行中的 exe 要"改名 → 写新 → 删旧"；`UninstallDisplayName`
  里的版本号会变旧（需额外写 HKCU 修正）；设计文档 §11「更新只经安装器」被推翻。
- 发布侧代价：**必须保留上一版 payload 作基线**（本地留存或从旧 Release 下载），并维护 N-1 基线矩阵；
  机器上当时没有 `zstd` / `bsdiff` / `xdelta3`，要引入并锁版本，或自研补丁格式。
- 结论：技术可行，但"有状态"（必须逐字节对上上一版）、新增工具链与基线依赖，性价比最差。

### B. 松散文件安装 + 文件级更新

- **安装包反倒更小（实测）**：把 publish 改成松散文件（402 个），用与真实一致的 `lzma2/ultra64 + solid`
  重新编译 → **45.9 MB**（现 59.7 MB，**−23%**，编译 70 秒）。原因是 Inno 能对 153.5 MB 原始数据做
  跨文件实心压缩，而现在的做法是对"已 deflate 过的数据"再压，只能捞回约 7%。
- **磁盘代价**：安装后 64.6 MB → **153.5 MB（+89 MB）**；好处是启动不再把 native 库自解压到 `%TEMP%`。
- **决定性实验**：Inno 的 `[Files]` 支持 `Flags: dontcopy`（能编译，探针包 8.9 MB 证明该文件确实没进包），
  但**它不会进卸载清单**——静默安装探针后检查 `unins000.dat`：真实复制的 exe 在册，
  两个 `dontcopy` 项都不在册。所以"增量安装包 = 全量清单 + 只打包变化文件"**行不通**：
  用户在下一次全量安装前卸载，会残留约 150 MB。
- 因此更新不能交给 Inno，只能由**应用自己替换文件**：manifest（目标版本每个文件的 path/size/sha256）
  → 客户端自己算本地哈希决定下哪些 → 校验后交给替换器（从 `%TEMP%` 副本以 `--apply-update` 启动，
  等主进程退出、备份、逐文件替换、失败回滚、重启、健康确认后删备份）。
- 相对 A 的最大优势：**无状态**——只按目标版本的文件快照比对，从任意旧版本都能升，
  本地文件被改坏也能自愈；发布侧不需要保留任何旧二进制，只要一份入库的基线 manifest。
- 已知残留点：**新增文件**不在首次安装写下的卸载清单里，需要更新器记录 + 后续安装器加
  `[UninstallRun] --cleanup-update-residue` 兜底。
- 估算：客户端 4–6 人日（替换器、回滚、状态机、自检、文案），发布侧 1 人日，文档 0.5 天，真机矩阵 1 天。

### C. framework-dependent（不携带运行时）

- 体积可降到约 11 MB，每次全量也只有 11 MB，改造面最小（csproj + 安装器前置检查 + 迁移说明）。
- 代价：要求用户安装 .NET 10 Desktop Runtime，与"免安装运行时"的定位冲突，属于产品取舍而非技术问题。

### D. 维持现状

- 每次 59.7 MB 全量，零维护成本，与 `docs/应用自更新设计.md` §13 的既有决策一致。

## 4. 三条路线对比

| 方案 | 更新体积 | 安装包 | 发布侧负担 | 客户端负担 | 主要风险 |
|---|---|---|---|---|---|
| D 现状 | 59.7 MB | 59.7 MB | 低 | 低 | 每次重下 60 MB |
| A 二进制补丁 | ≈2 MB | 59.7 MB | **高**（保留旧 payload、基线矩阵、自研补丁格式） | 中 | 基线对不上即全量；运行时升级版补丁≈全量 |
| B 松散 + 文件级 | ≈2 MB | **45.9 MB** | 中（manifest、更新包、多一个附件） | 中高（替换器 + 回滚） | 磁盘 +89 MB；新增文件的卸载残留需兜底 |
| C framework-dependent | 11 MB | ≈11 MB | 低 | 低 | 要求用户装 .NET 10 Desktop Runtime |

## 5. 结论：暂不实施

理由：

1. **收益与规模不匹配**：内测用户量小，60 MB 一次下载不构成实际痛点；而三条路线都要约一周投入，
   并新增一条需要**长期维护**的升级路径（每次发布多产物、多校验、多真机用例）。
2. **风险与复杂度集中在自己写替换器上**：B 方案最省心（无基线二进制），但仍要把"退出后替换 + 回滚 +
   健康确认"完整实现并长期回归，才能换来"每次少下 58 MB"。
3. **与既有决策一致**：`docs/应用自更新设计.md` §13 已明确"不做增量/差分更新（内测人少，67 MB 可接受）"。

## 6. 若将来重启，建议的顺序

1. **先只改打包形态**（松散文件 + 全量 Setup 45.9 MB + 便携 zip），自更新继续下载全量 Setup。
   这一步纯打包改动、风险最低，收益是安装包 −23% 与启动不再自解压；顺带用一两版验证
   松散形态下"安装 / 覆盖升级 / 卸载"是否干净（本次探针已确认：`[Files]` 全量列出时卸载清单才是完整的）。
2. **再上文件级更新**（manifest + 替换器），才有"每次 ≈2 MB"。
3. 可选优化：把三张数据表与语言表从内嵌改为 `{app}\Assets` 散文件，让"应用本体"从 11.3 MB 缩到约 1 MB；
   这会改变加载路径（现为 `GetManifestResourceStream`）与自检，建议等文件级更新稳定之后再评估。

需要先拍板的两件事：**+89 MB 磁盘占用是否可接受**、**便携形态改成"文件夹 zip"是否可接受**。

## 7. 复现方法（复测这些数字）

| 数字 | 复现要点 |
|---|---|
| 分组体积 / 压缩后占比 | `dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=false`（得 402 个松散文件），逐文件用 `DeflateStream` 压一遍求和 |
| 跨版本增量 | 用 `git worktree add <临时目录> v<旧版本>` 重建旧 payload，再对两版 payload 做**内容定界**切块比对（定长块会严重低估） |
| 松散安装包体积 | 用 `ISCC.exe` 编译一个指向松散目录的临时 `.iss`（`Compression=lzma2/ultra64` + `SolidCompression=yes`），读产物大小 |
| `dontcopy` 语义 | 建探针包（1 个真实文件 + 若干 `dontcopy`），`/VERYSILENT` 装到临时目录后，用 UTF-16 搜索 `unins000.dat` 里的文件名，再静默卸载 |
| 运行时是否随版本变 | 把 `dist\publish` 里的运行时 DLL 与 `C:\Program Files\dotnet\shared\{Microsoft.NETCore.App,Microsoft.WindowsDesktop.App}\<版本>` 的同名文件比 SHA256 |

> 探针安装包与临时目录在评估结束后已全部清理（含 `HKCU` 卸载项）；本评估未改动任何代码或发布脚本。
